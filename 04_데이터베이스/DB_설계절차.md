# 데이터베이스 설계 절차

## 핵심 요약
> **요구사항 분석 → 개념 설계 → 논리 설계 → 물리 설계 → 구현**
> 암기법: **"요개논물구"**

---

## 실전 예시: "배달앱 주문 시스템" 만들기

사장님이 "배달앱 만들어주세요"라고 하면, DB를 이 순서로 설계한다:

---

### 1단계: 요구사항 분석 — "뭐가 필요해요?"

고객, 사장님, 라이더한테 물어보고 정리하는 단계.

```
[인터뷰 결과]

고객: "메뉴 보고 주문하고, 배달 추적하고 싶어요"
사장님: "주문 들어오면 확인하고, 매출 보고 싶어요"
라이더: "배달 목록 보고, 완료 처리하고 싶어요"

[정리된 요구사항]
- 고객은 회원가입 후 주문할 수 있다
- 하나의 주문에 여러 메뉴를 담을 수 있다
- 각 가게는 여러 메뉴를 등록할 수 있다
- 라이더 한 명이 한 번에 하나의 주문을 배달한다
- 주문 상태: 접수 → 조리중 → 배달중 → 완료
- 고객은 배달 완료 후 리뷰를 작성할 수 있다
```

→ **산출물**: 요구사항 명세서
→ 아직 기술적인 건 하나도 없음. 그냥 "뭐 해야 하는지" 정리

---

### 2단계: 개념 설계 — "ER 다이어그램 + 트랜잭션 인터페이스 설계"

요구사항을 보고 **2가지를 병행**해서 설계하는 단계.
이 단계에서는 특정 DBMS(MySQL, Oracle 등)를 **신경 쓰지 않음**.

#### ① 스키마 설계 — "데이터를 어떤 구조로 담을까?"

```
[엔티티 도출]
고객, 가게, 메뉴, 주문, 주문상세, 라이더, 리뷰

[ER 다이어그램]

고객(1) ──주문하다──(N) 주문
                          │
                        (1:N)
                          │
                      주문상세(N) ──포함하다──(1) 메뉴

가게(1) ──등록하다──(N) 메뉴

라이더(1) ──배달하다──(N) 주문

고객(1) ──작성하다──(N) 리뷰 ──(N)대상──(1) 가게
```

→ 데이터 중심: "어떤 데이터가 있고 서로 어떤 관계인가?"

#### ② 트랜잭션 인터페이스 설계 — "데이터를 어떻게 사용할까?"

```
[트랜잭션 목록]

T1. 주문하기
    입력: 고객ID, 가게ID, [메뉴ID + 수량] 목록
    처리: 주문 생성 → 주문상세 생성 → 총금액 계산
    출력: 주문ID, 예상 배달시간

T2. 주문 조회
    입력: 고객ID
    처리: 해당 고객의 주문 목록 조회
    출력: [주문ID, 가게명, 총금액, 상태] 목록

T3. 주문 상태 변경
    입력: 주문ID, 변경할 상태
    처리: 주문 상태 업데이트 (접수→조리중→배달중→완료)
    출력: 변경 결과

T4. 리뷰 작성
    입력: 고객ID, 주문ID, 별점, 내용
    처리: 배달 완료된 주문인지 확인 → 리뷰 생성
    출력: 리뷰ID
```

→ 기능 중심: "이 DB로 어떤 작업을 할 것인가?"
→ 스키마 설계가 **그릇 모양**이면, 트랜잭션 인터페이스 설계는 **그릇 사용법**
→ ⚠️ 아직 **SQL을 짜는 게 아님!** "뭘 할지" 정의만 하는 것. 실제 DML은 구현 단계에서 작성.

#### 트랜잭션 인터페이스 설계 → 구현 단계 변환 예시

```
[개념 설계: 트랜잭션 인터페이스 설계]      [구현: 실제 DML]

T1. 주문하기                              INSERT INTO 주문 (고객ID, 가게ID, 총금액)
    입력: 고객ID, 가게ID, 메뉴목록    →    VALUES (1, 5, 25000);
    처리: 주문 생성, 금액 계산              INSERT INTO 주문상세 (주문ID, 메뉴ID, 수량)
    출력: 주문ID                           VALUES (1, 3, 2);

T2. 주문 조회                              SELECT 주문ID, 가게명, 총금액, 상태
    입력: 고객ID                     →    FROM 주문
    처리: 주문 목록 조회                    WHERE 고객ID = 1;
    출력: 주문 목록

T3. 주문 상태 변경                          UPDATE 주문
    입력: 주문ID, 상태               →    SET 상태 = '배달중'
    처리: 상태 업데이트                     WHERE 주문ID = 1;

T4. 리뷰 작성                              INSERT INTO 리뷰 (고객ID, 주문ID, 별점, 내용)
    입력: 고객ID, 주문ID, 별점, 내용  →    VALUES (1, 1, 5, '맛있어요');
    처리: 리뷰 생성
```

→ 개발자 비유: 트랜잭션 인터페이스 설계 = **API 명세서(Swagger)**, 구현 = **실제 코드 작성**

→ **산출물**: ER 다이어그램 + 트랜잭션 인터페이스 명세
→ DBMS 독립적 (어떤 DB 쓸지 아직 안 정함)
→ 시험에서 **"개념 설계 = ER 다이어그램 = 트랜잭션 인터페이스 설계"** 이 연결이 중요!

---

### 3단계: 논리 설계 — "테이블로 변환"

ER 다이어그램을 **관계형 모델(테이블)**로 변환하는 단계.
정규화도 이 단계에서 수행.

```
[ER → 테이블 변환 결과]

고객 (고객ID(PK), 이름, 전화번호, 주소, 가입일)

가게 (가게ID(PK), 가게명, 사업자번호, 주소, 전화번호)

메뉴 (메뉴ID(PK), 가게ID(FK), 메뉴명, 가격, 카테고리)

주문 (주문ID(PK), 고객ID(FK), 가게ID(FK), 라이더ID(FK),
      주문일시, 총금액, 상태, 배달주소)

주문상세 (주문ID(FK), 메뉴ID(FK), 수량, 소계)
         PK = (주문ID, 메뉴ID)

라이더 (라이더ID(PK), 이름, 전화번호, 차량번호)

리뷰 (리뷰ID(PK), 고객ID(FK), 가게ID(FK), 주문ID(FK),
      별점, 내용, 작성일)
```

```
[정규화 수행 예시]

변경 전 (비정규):
주문 테이블에 [메뉴명, 메뉴가격, 수량] 컬럼이 직접 들어있음
→ 메뉴 2개 주문하면? 컬럼을 메뉴명1, 메뉴명2로 늘려야 함 (반복 그룹!)

변경 후 (정규화):
주문 테이블 + 주문상세 테이블로 분리
→ 메뉴가 몇 개든 주문상세에 행(row)만 추가하면 됨
```

→ **산출물**: 관계 스키마 (테이블 명세), 정규화 결과
→ 아직 DBMS 종속적인 것(ENGINE, INDEX)은 안 정함
→ 시험에서 **"논리 설계 = 정규화"** 이 연결이 중요!

---

### 4단계: 물리 설계 — "성능 튜닝 설계"

실제 사용할 DBMS를 정하고, **인덱스, 파티션, 저장 구조** 등을 결정하는 단계.
= 내부 스키마를 설계하는 것!

```sql
-- DBMS 선정: MySQL 8.0 (InnoDB)

-- 주문 테이블: 주문량이 많으니 날짜별 파티셔닝
-- → 월별로 데이터 분리해서 검색 속도 향상
PARTITION BY RANGE (YEAR(주문일시) * 100 + MONTH(주문일시)) (
    PARTITION p202601 VALUES LESS THAN (202602),
    PARTITION p202602 VALUES LESS THAN (202603)
);

-- 자주 검색하는 컬럼에 인덱스 설정
CREATE INDEX idx_주문_고객 ON 주문(고객ID);      -- 고객별 주문내역 조회용
CREATE INDEX idx_주문_상태 ON 주문(상태);         -- 상태별 필터링용
CREATE INDEX idx_메뉴_가게 ON 메뉴(가게ID);       -- 가게별 메뉴 조회용

-- 테이블별 용량 산정
-- 고객: 약 100만 건 × 200byte = 약 200MB
-- 주문: 월 50만 건 × 300byte = 월 약 150MB
-- 주문상세: 주문당 평균 3건 → 월 150만 건

-- 반정규화 결정
-- 주문 테이블에 가게명 중복 저장 (매번 JOIN하면 느리니까)
-- 정규화 원칙에는 어긋나지만 성능을 위해 의도적으로 중복
```

→ **산출물**: 물리 스키마, 인덱스 설계, 용량 산정, 반정규화 결정
→ 시험에서 **"물리 설계 = 인덱스, 반정규화, 성능"** 이 연결이 중요!

---

### 5단계: 구현 — "실제로 만들기"

물리 설계를 바탕으로 **실제 SQL을 실행**해서 DB를 만드는 단계.

```sql
-- 실제 DDL 실행
CREATE TABLE 고객 (
    고객ID    INT          AUTO_INCREMENT PRIMARY KEY,
    이름      VARCHAR(20)  NOT NULL,
    전화번호  VARCHAR(15)  NOT NULL UNIQUE,
    주소      VARCHAR(100),
    가입일    DATETIME     DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE 주문 (
    주문ID    INT          AUTO_INCREMENT PRIMARY KEY,
    고객ID    INT          NOT NULL,
    가게ID    INT          NOT NULL,
    라이더ID  INT,
    주문일시  DATETIME     DEFAULT CURRENT_TIMESTAMP,
    총금액    INT          NOT NULL,
    상태      ENUM('접수','조리중','배달중','완료') DEFAULT '접수',
    배달주소  VARCHAR(100) NOT NULL,
    가게명    VARCHAR(30),  -- 반정규화: 성능 위해 중복 저장
    FOREIGN KEY (고객ID) REFERENCES 고객(고객ID),
    FOREIGN KEY (가게ID) REFERENCES 가게(가게ID),
    FOREIGN KEY (라이더ID) REFERENCES 라이더(라이더ID)
) ENGINE=InnoDB;

-- 인덱스 생성
CREATE INDEX idx_주문_고객 ON 주문(고객ID);
CREATE INDEX idx_주문_상태 ON 주문(상태);

-- 뷰 생성 (외부 스키마)
CREATE VIEW 고객_주문내역뷰 AS
SELECT o.주문ID, o.주문일시, o.가게명, o.총금액, o.상태
FROM 주문 o
WHERE o.고객ID = @현재_고객ID;

-- 권한 설정 (DCL)
GRANT SELECT ON 고객_주문내역뷰 TO 'app_customer'@'%';
GRANT ALL ON 주문 TO 'app_admin'@'%';

-- 테스트 데이터 삽입
INSERT INTO 고객 (이름, 전화번호, 주소)
VALUES ('홍길동', '010-1234-5678', '서울시 강남구');
```

→ **산출물**: 실제 동작하는 데이터베이스
→ DDL + DML + DCL 전부 사용

## 5단계 한눈에 비교

| 단계 | 핵심 질문 | 산출물 | 시험 키워드 |
|------|----------|--------|-----------|
| 요구사항 분석 | **뭐가** 필요해? | 요구사항 명세서 | 인터뷰, 명세서 |
| 개념 설계 | **뭐와 뭐**가 관계있어? + **어떻게 쓸까?** | **ER 다이어그램** + 트랜잭션 인터페이스 | E-R 모델, 트랜잭션 인터페이스 설계 |
| 논리 설계 | **테이블**로 어떻게 나눠? | 관계 스키마 | **정규화**, 테이블 변환 |
| 물리 설계 | **성능**은 어떻게 올려? | 물리 스키마 | **인덱스, 반정규화**, 용량 산정 |
| 구현 | **실제로** 만들자! | DB 자체 | DDL/DML/DCL 실행 |

## 시험 빈출 포인트

### ⚠️ 이 매칭이 가장 많이 나옴!
- **개념 설계** = ER 다이어그램 = DBMS 독립적
- **논리 설계** = 정규화 = 테이블 변환
- **물리 설계** = 인덱스 + 반정규화 = 성능 최적화

### ⚠️ 헷갈리는 함정
| 질문 | 답 |
|------|-----|
| ER 다이어그램은 어느 단계? | **개념 설계** (논리 설계 아님!) |
| 정규화는 어느 단계? | **논리 설계** (개념 설계 아님!) |
| 반정규화는 어느 단계? | **물리 설계** (논리 설계에서 정규화 → 물리 설계에서 반정규화) |
| DBMS를 정하는 건 어느 단계? | **물리 설계** |
| 트랜잭션 분석은 어느 단계? | **물리 설계** |
| 트랜잭션 인터페이스 설계는 어느 단계? | **개념 설계** (물리 설계 아님!) |

### ⚠️ 핵심 판단 기준: "왜 하는가?"로 구분!

테이블 구조를 바꾸는 행위라도 **이유**에 따라 단계가 달라진다:

| 이유 | 단계 | 예시 |
|------|------|------|
| **올바른 구조** (중복 제거, 무결성) | **논리 설계** | 정규화, PK/FK 설정 |
| **빠른 성능** (속도, 용량, 응답시간) | **물리 설계** | 반정규화, 인덱스, 파티셔닝 |

→ 반정규화는 테이블 구조를 바꾸지만 **목적이 "성능 향상"**이므로 물리 설계!
→ **"올바름 = 논리, 빠름 = 물리"**

## 기출 키워드
`요구사항 분석` `개념 설계` `논리 설계` `물리 설계` `구현` `ER 다이어그램` `정규화` `반정규화` `인덱스` `트랜잭션 분석` `용량 산정` `DBMS 독립적`
