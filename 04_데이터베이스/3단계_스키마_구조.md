# 3단계 스키마 구조 (ANSI/SPARC)

## 핵심 요약
> DB를 **외부 → 개념 → 내부** 3개 층으로 나눈 구조. 이 덕분에 **데이터 독립성**이 생긴다.

## 주요 개념

### ⚠️ 이름이 여러 개! (시험에서 별명으로 낚음)

| 층 | 정식 이름 | 별명 | 의미 | 개수 |
|----|----------|------|------|------|
| 상 | 외부 스키마 | **서브 스키마** | 사용자별 뷰 | **여러 개** 가능 |
| 중 | 개념 스키마 | **스키마** | DB 전체 논리 구조 | **1개** |
| 하 | 내부 스키마 | **물리 스키마**, 저장 스키마 | 물리적 저장 구조 | **1개** |

---

## 구체적 예시: "학교 성적 DB"

하나의 DB를 3단계로 나눠서 보면 이렇게 됨:

### 외부 스키마 (= 서브 스키마) — 사용자마다 다르게 보임

```sql
-- 외부 스키마 A: 학생용 뷰
CREATE VIEW 학생_성적뷰 AS
SELECT s.학번, s.이름, c.과목명, g.점수
FROM 학생 s
JOIN 성적 g ON s.학번 = g.학번
JOIN 과목 c ON g.과목코드 = c.과목코드
WHERE s.학번 = :현재_로그인_학번;

-- 외부 스키마 B: 교수용 뷰
CREATE VIEW 교수_성적관리뷰 AS
SELECT s.학번, s.이름, g.점수, g.등급
FROM 학생 s
JOIN 성적 g ON s.학번 = g.학번
WHERE g.과목코드 = :담당_과목코드;

-- 외부 스키마 C: 학부모용 뷰
CREATE VIEW 학부모_자녀뷰 AS
SELECT s.이름, AVG(g.점수) AS 전체평균
FROM 학생 s
JOIN 성적 g ON s.학번 = g.학번
GROUP BY s.학번, s.이름;
```

→ 같은 DB인데 **누가 보느냐에 따라 VIEW가 다름**
→ 그래서 외부 스키마는 **여러 개** 존재

### 개념 스키마 (= 스키마) — DB 전체 설계도 (딱 1개)

```sql
-- 우리가 평소 짜는 CREATE TABLE이 개념 스키마
CREATE TABLE 학생 (
    학번    INT         PRIMARY KEY,
    이름    VARCHAR(20) NOT NULL,
    학과    VARCHAR(30),
    학년    INT         CHECK (학년 BETWEEN 1 AND 4)
);

CREATE TABLE 과목 (
    과목코드 CHAR(5)     PRIMARY KEY,
    과목명   VARCHAR(30) NOT NULL,
    학점     INT,
    담당교수 VARCHAR(20)
);

CREATE TABLE 성적 (
    학번     INT   REFERENCES 학생(학번),
    과목코드 CHAR(5) REFERENCES 과목(과목코드),
    점수     INT   CHECK (점수 BETWEEN 0 AND 100),
    등급     CHAR(2),
    PRIMARY KEY (학번, 과목코드)
);
```

→ **테이블, 컬럼, PK/FK, 제약조건** = 개념 스키마
→ 개발자가 가장 많이 접하는 영역

### 내부 스키마 (= 물리 스키마) — 물리적 저장/성능 설정 (딱 1개)

```sql
-- 스토리지 엔진 선택
CREATE TABLE 학생 (
    ...
) ENGINE=InnoDB              -- InnoDB vs MyISAM → 내부 스키마
  ROW_FORMAT=COMPRESSED      -- 행 압축 방식 → 내부 스키마
  TABLESPACE ts_student;     -- 테이블스페이스 지정 → 내부 스키마

-- 인덱스 설정
CREATE INDEX idx_학생_이름 ON 학생(이름);           -- B+트리 인덱스
CREATE INDEX idx_성적_점수 ON 성적(점수) USING HASH; -- 해시 인덱스

-- 파티셔닝
ALTER TABLE 성적 PARTITION BY RANGE (학번) (
    PARTITION p1 VALUES LESS THAN (2023000),
    PARTITION p2 VALUES LESS THAN (2024000),
    PARTITION p3 VALUES LESS THAN (2025000)
);

-- 클러스터링 (InnoDB에서 PK 기준 자동 클러스터링)
-- 학번 기준으로 물리적으로 정렬되어 디스크에 저장됨
```

→ **성능 튜닝할 때 건드리는 것** = 전부 내부 스키마
→ 인덱스, 파티션, 엔진, 압축, 테이블스페이스 등

#### 내부 스키마가 다루는 것 정리
| 항목 | 예시 | 설명 |
|------|------|------|
| 인덱스 | `CREATE INDEX`, B+트리, 해시 | 검색 속도 최적화 |
| 스토리지 엔진 | InnoDB, MyISAM | 트랜잭션 지원 여부 등 |
| 파티셔닝 | RANGE, HASH, LIST | 대용량 테이블 분할 |
| 테이블스페이스 | `TABLESPACE ts_name` | 물리적 파일 위치 지정 |
| 레코드 포맷 | ROW_FORMAT, 압축 | 디스크 저장 형식 |
| 컬럼 물리 크기 | INT=4byte, VARCHAR(50) | 실제 바이트 크기 |
| 클러스터링 | PK 기준 물리 정렬 | 디스크 저장 순서 |
| 버퍼/캐시 | buffer_pool_size | 메모리 설정 |

## 개발자 관점 3단계 한눈에

```
┌─────────────────────────────────────────────────────┐
│  외부 스키마        CREATE VIEW ...                  │
│  (서브 스키마)      사용자/앱마다 다른 뷰             │
│                    → 여러 개 가능                    │
├─────────────────────────────────────────────────────┤
│  개념 스키마        CREATE TABLE ...                 │
│  (스키마)          테이블, PK/FK, 제약조건            │
│                    → 딱 1개                          │
├─────────────────────────────────────────────────────┤
│  내부 스키마        ENGINE=, INDEX, PARTITION ...     │
│  (물리 스키마)      인덱스, 엔진, 파티션, 압축         │
│                    → 딱 1개                          │
└─────────────────────────────────────────────────────┘
```

## 데이터 독립성 — 예시로 이해

### 물리적 독립성 (내부 변경 → 개념 영향 없음)
```sql
-- 변경 전
CREATE INDEX idx_점수 ON 성적(점수) USING HASH;

-- 변경 후: 인덱스 방식을 바꿈
DROP INDEX idx_점수 ON 성적;
CREATE INDEX idx_점수 ON 성적(점수) USING BTREE;
```
→ 인덱스(내부 스키마)를 바꿔도 `SELECT * FROM 성적 WHERE 점수 > 90`은 **그대로 동작!**
→ 개념 스키마(테이블 구조)는 건드리지 않음

### 논리적 독립성 (개념 변경 → 외부 영향 없음)
```sql
-- 변경 전: 학생 테이블
CREATE TABLE 학생 (학번 INT PK, 이름 VARCHAR, 학과 VARCHAR, 학년 INT);

-- 변경 후: 전화번호 컬럼 추가
ALTER TABLE 학생 ADD COLUMN 전화번호 VARCHAR(15);
```
→ 테이블에 컬럼을 추가(개념 스키마 변경)해도 기존 `학생_성적뷰`(외부 스키마)는 **그대로 작동!**
→ 뷰에서 전화번호를 SELECT하지 않으니 영향 없음

## 스키마와 SQL의 관계

### 스키마는 모두 DDL로 정의한다!
| 스키마 | 정의 도구 | 실제 SQL 예시 |
|--------|----------|-------------|
| 외부 스키마 | **DDL** | `CREATE VIEW` |
| 개념 스키마 | **DDL** | `CREATE TABLE` |
| 내부 스키마 | **DDL** | `CREATE INDEX`, `ENGINE=`, `PARTITION BY` |

→ 스키마 = 구조/틀 = **정의(Definition)** = DDL
→ DCL(제어어)은 구조가 아니라 **권한 관리**(GRANT/REVOKE)이므로 스키마 정의와 무관

## 시험 빈출 포인트

### ⚠️ 단골 함정

| 함정 유형 | 주의 |
|-----------|------|
| 별명 바꿔치기 | "서브 스키마"가 나오면 = 외부 스키마 |
| 개수 질문 | 외부 스키마만 **여러 개**, 나머지는 **1개** |
| 독립성 방향 | 논리적 독립성: 개념↔외부 / 물리적 독립성: 내부↔개념 |
| 종속성 vs 독립성 | 3단계 구조 → **독립성** 제공 ✅ (종속성 ❌) |
| 관리 주체 | 외부=사용자(응용 프로그래머), 개념/내부=DBA |

## 기출 키워드
`3단계 스키마` `외부 스키마` `서브 스키마` `개념 스키마` `내부 스키마` `물리 스키마` `논리적 독립성` `물리적 독립성` `외부/개념 매핑` `개념/내부 매핑` `DBA` `ANSI/SPARC`
