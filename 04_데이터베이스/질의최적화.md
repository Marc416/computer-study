# 질의 최적화 (Query Optimization)

## 핵심 요약
> **"먼저 줄이고, 나중에 합쳐라"**
> 추출(Selection)과 프로젝션(Projection)을 먼저 수행해서 데이터를 줄인 뒤, 조인을 나중에 수행하면 처리량이 대폭 감소한다.

## 주요 개념

### 질의 최적화란?
- 같은 결과를 내는 여러 실행 방법 중 **가장 빠른 방법**을 찾는 것
- 비유: 이사할 때 짐을 100박스 다 옮긴 후 버리기 vs 먼저 버리고 30박스만 옮기기

### 핵심 최적화 규칙

| 규칙 | 설명 | 비유 |
|------|------|------|
| **추출(Selection) 먼저** | WHERE 조건 필터링을 가장 먼저 수행 | 짐부터 줄여라 |
| **프로젝션(Projection) 먼저** | 필요한 컬럼만 먼저 골라냄 | 안 쓸 짐은 버려라 |
| **조인은 최대한 나중에** | 데이터가 줄어든 후 조인 | 짐 줄인 다음에 합쳐라 |
| **카티션 곱(Cartesian Product) 회피** | 조건 없는 곱은 최대한 피함 | 무작정 전부 합치지 마라 |

## SQL 예시로 이해하기

### 상황
```
사원 테이블 (10만 건): 사번, 이름, 부서코드, 지역
부서 테이블 (100건): 부서코드, 부서명

목표: "서울에 사는 사원의 이름과 부서명을 구하라"
```

### ❌ 최적화 전 (조인 먼저 → 추출 나중)
```sql
SELECT 이름, 부서명
FROM 사원, 부서
WHERE 사원.부서코드 = 부서.부서코드
  AND 지역 = '서울';
```

DB 내부 처리:
1. 사원 × 부서 **전체 조인** → 10만 × 100 = **1000만 건**
2. 지역 = '서울' 필터 → 3만 건
3. 이름, 부서명 추출

### ✅ 최적화 후 (추출 먼저 → 조인 나중)
```sql
SELECT 이름, 부서명
FROM (SELECT 이름, 부서코드 FROM 사원 WHERE 지역 = '서울') AS 서울사원,
     부서
WHERE 서울사원.부서코드 = 부서.부서코드;
```

DB 내부 처리:
1. 사원에서 지역 = '서울' **먼저 추출** → **3만 건**
2. 필요한 컬럼만 프로젝션 → 더 가벼워짐
3. 3만 건 × 부서 조인 → **300만 건**만 처리

### 처리량 비교

| | 최적화 전 | 최적화 후 |
|---|---|---|
| 조인 처리량 | **1000만 건** | **300만 건** |
| 개선율 | - | **약 70% 감소** |

## 관계대수와 연결

질의 최적화는 **관계대수 연산 트리**의 순서를 바꾸는 것:
- σ (Selection, 추출) → 트리 아래로 내림 (먼저 실행되도록)
- π (Projection, 프로젝션) → 트리 아래로 내림
- ⋈ (Join, 조인) → 트리 위로 올림 (나중에 실행되도록)

## 시험 빈출 포인트
- "추출 연산을 가능한 한 **일찍** 수행" → 질의 최적화의 핵심
- 같은 SQL이라도 **실행 순서에 따라 성능 차이**가 큼
- DB 옵티마이저가 자동으로 최적화하지만, 시험에서는 **원리**를 묻는다
- 카티션 곱(조건 없는 조인)은 데이터 폭발 → 반드시 피해야 함

## 헷갈리는 개념 비교
| 구분 | 추출 (Selection) | 프로젝션 (Projection) |
|------|-----------------|---------------------|
| 기호 | σ (시그마) | π (파이) |
| 하는 일 | **행(튜플)** 필터링 | **열(속성)** 필터링 |
| SQL | WHERE 절 | SELECT 절의 컬럼 지정 |
| 비유 | 줄에서 키 180 이상만 남겨라 | 이름, 나이만 보여줘 |

## 질의 트리(Query Tree) 구조

질의 트리는 SQL문을 DB가 내부적으로 변환한 **실행 순서도**이다.
**아래에서 위로** 실행된다. (아래 노드 = 먼저, 위 노드 = 나중)

### 최적화 전 (비효율적)
```
        결과 (5. 최종 출력)
         ↑
     π 이름, 부서명 (4. 필요한 컬럼만 추출)
         ↑
     σ 지역='서울' (3. 서울만 필터) ← 늦게 필터링
         ↑
       ⋈ 조인 (2. 두 테이블 합치기) ← 10만×100 = 1000만 건!
      ↗     ↖
   사원      부서 (1. 테이블 읽기)
```

### 최적화 후 (효율적) — σ를 아래로 내림
```
        결과
         ↑
     π 이름, 부서명
         ↑
       ⋈ 조인 ← 3만×100 = 300만 건으로 줄어듦!
      ↗     ↖
 σ 지역='서울'   부서    ← 선택을 아래로 내려서 먼저 실행!
     ↑
    사원
```

> **핵심**: 노드를 아래로 내린다 = 그 연산을 더 먼저 실행한다 = 데이터를 일찍 줄인다

## 카티션 프로덕트 (Cartesian Product)
- **조건 없이** 두 테이블의 모든 행을 곱하는 연산
- A(2행) × B(3행) = **6행** → 데이터가 폭발적으로 증가
- 비유: 2명 × 3개 메뉴 = 가능한 조합 6가지를 전부 만드는 것
- **비용이 매우 비싸서** 최적화 시 반드시 피하거나 조인으로 변환해야 함
- 카티션 프로덕트 + 선택 조건(조인 조건) → **조인 연산으로 변환** 가능

## 경험적 최적화 규칙 (기출 134번 유형)

질의 트리는 **아래에서 위로** 실행됨 (아래 = 먼저, 위 = 나중)

| 번호 | 규칙 | 핵심 |
|------|------|------|
| 1 | 선택(σ)은 가능한 한 **아래로** (먼저 실행) | 데이터를 일찍 줄여라 |
| 2 | **가장 제한적인** 선택을 **가장 먼저** (= 하위 노드) | 가장 많이 걸러내는 조건을 제일 먼저! |
| 3 | 추출(π)도 **일찍** 수행 | 필요한 컬럼만 빨리 골라라 |
| 4 | 카티션 프로덕트는 리프 노드에서 **일으키지 않도록** | 비싼 연산 피하기 |
| 5 | 카티션 프로덕트 + 선택(조인 조건) → **조인으로 변환** | 합체시켜서 효율화 |

⚠️ **함정 선지**: "가장 제한적인 선택을 **나중에/상위 노드**로" → **틀린 설명!** (정반대임)
