# 회복과 동시성 제어

## 핵심 요약
> **회복(Recovery)** = 시스템 장애 발생 시 데이터베이스를 정상 상태로 되돌리는 것
> 핵심은 **REDO**와 **UNDO** 두 가지 연산, 그리고 **어떤 회복 기법을 쓰느냐**에 따라 적용이 달라진다

---

## 주요 개념

### 1. 트랜잭션(Transaction)이란?
데이터베이스에서 하나의 작업 단위. "전부 성공 아니면 전부 취소"가 원칙이다.

**ACID 성질:**

| 성질 | 의미 | 쉬운 비유 |
|------|------|-----------|
| **A**tomicity (원자성) | 전부 실행 or 전부 취소 | 은행 송금: 보내기+받기 둘 다 되거나, 둘 다 안 되거나 |
| **C**onsistency (일관성) | 실행 전후 DB 상태가 일관적 | 잔액 합계가 송금 전후 동일 |
| **I**solation (격리성) | 다른 트랜잭션이 끼어들 수 없음 | ATM 사용 중 다른 사람이 못 건드림 |
| **D**urability (영속성) | 커밋 완료되면 영구 보존 | 저장 버튼 누르면 확실히 저장됨 |

### 2. 회복 연산: REDO vs UNDO

| 구분 | REDO (재실행) | UNDO (취소) |
|------|--------------|-------------|
| **언제?** | Commit **된** 트랜잭션 | Commit **안 된** 트랜잭션 |
| **뭘 하나?** | **new 값**으로 다시 반영 | **old 값**으로 되돌림 |
| **비유** | "배송완료 찍힌 택배 재확인" | "배송 전 택배 회수" |

### 3. 로그(Log) 읽는 법
- `<Tn, Start>` → 트랜잭션 Tn 시작
- `<Tn, A, old, new>` → Tn이 데이터 A를 old에서 new로 변경
- `<Tn, Commit>` → Tn 완료 (확정)
- `<Tn, Abort>` → Tn 취소
- `<Checkpoint>` → 검사점 (이 시점까지는 안전하게 저장됨)

### 4. 검사점(Checkpoint)
- "여기까지는 확실히 DB에 반영했다"는 표시
- 회복 시 Checkpoint **이전에 Commit 완료된 트랜잭션**은 무시해도 됨
- Checkpoint **이후**의 트랜잭션만 분석하면 된다

## 회복 기법 비교 (가장 중요!)

### 지연갱신 (Deferred Update)
> **"커밋 전에는 DB를 절대 안 건드린다"**

| 트랜잭션 상태 | 회복 연산 | 이유 |
|--------------|----------|------|
| Commit 완료 | **REDO** | DB에 반영해줘야 하니까 |
| Commit 안 됨 | **No operation** (무시) | 애초에 DB를 안 건드렸으니까 |

- **UNDO가 필요 없다!** (DB를 안 건드렸으므로 되돌릴 것이 없음)
- 비유: 연필로 답안 작성 중 → "제출" 전에 시험장 정전 → 원본 답안지는 깨끗, 아무것도 안 해도 됨

### 즉시갱신 (Immediate Update)
> **"커밋 전에도 DB에 바로 반영한다"**

| 트랜잭션 상태 | 회복 연산 | 이유 |
|--------------|----------|------|
| Commit 완료 | **REDO** | 확실히 반영되었는지 재확인 |
| Commit 안 됨 | **UNDO** | 이미 DB를 건드렸으니 되돌려야 함 |

- **UNDO와 REDO 둘 다 필요**
- 비유: 볼펜으로 답안 작성 중 → 정전 → 이미 쓴 건 지우개로 지워야 함(UNDO)

### 한눈에 비교

| 구분 | 지연갱신 | 즉시갱신 |
|------|---------|---------|
| DB 반영 시점 | Commit 후 | 즉시 |
| 필요한 연산 | **REDO만** | **REDO + UNDO** |
| Commit 안 된 것 | 무시 | UNDO |
| 별칭 | NO-UNDO/REDO | UNDO/REDO |

## 기출문제 풀이 전략

### 문제 풀이 3단계

**1단계: 회복 기법 확인**
- "지연갱신" → UNDO 없음, REDO만
- "즉시갱신" → UNDO + REDO 둘 다

**2단계: Checkpoint 기준으로 나누기**
- Checkpoint 이전에 Commit → **무시 (No operation)**
- Checkpoint 이후에 Commit → **REDO**
- Commit 안 됨 → 기법에 따라 다름 (지연=무시, 즉시=UNDO)

**3단계: 각 트랜잭션 판정**

### 기출문제 예시 (2012 국가직)

**로그:**
```
<T1, Start>
<T1, A, 900, 1000>
<T1, Commit>
<T4, Start>
<T3, Start>
<T2, Start>
<Checkpoint>
<T2, B, 2100, 2200>
<T2, Commit>
<T3, C, 1700, 1800>
<T3, Abort>
<T4, A, 600, 700>
시스템 실패
```

**분석 (지연갱신 방식):**

| 트랜잭션 | Checkpoint 기준 | Commit 여부 | 회복 연산 |
|----------|----------------|------------|----------|
| T1 | 이전에 Commit 완료 | ✅ Commit | **No operation** |
| T2 | 이후에 Commit | ✅ Commit | **REDO** (B→2200) |
| T3 | - | ❌ Abort | **No operation** |
| T4 | - | ❌ 미완료 | **No operation** |

**정답: ④ T4 : undo** (지연갱신에서는 UNDO를 하지 않으므로 옳지 않은 연산)

# 동시성 제어 - 로킹(Locking)

## 핵심 요약
> **로킹** = 한 트랜잭션이 데이터를 쓰는 동안 다른 트랜잭션이 못 건드리게 "잠금"을 거는 기법
> 핵심은 **2단계 로킹(2PL)**과 **로킹 단위(Granularity)**, 그리고 **교착상태(Deadlock)**

---

## 주요 개념

### 1. 로크(Lock)란?
화장실 문 잠금장치와 같다. 누군가 들어가서 잠그면(Lock), 다른 사람은 기다려야 하고, 나올 때 잠금을 풀면(Unlock) 다음 사람이 들어간다.

- **Lock** → 데이터에 잠금을 건다 (나만 쓸게!)
- **Unlock** → 잠금을 푼다 (다 썼어, 이제 써!)

### 2. 로킹 단위(Granularity)
잠금을 거는 범위의 크기. "화장실 한 칸만 잠글까, 건물 전체를 잠글까?"

| 로킹 단위 | 예시 | 병행성 | 관리 복잡도 | 로크 수 |
|-----------|------|--------|------------|--------|
| **크다** (DB, 테이블) | 건물 전체 잠금 | ⬇ 낮음 | ⬇ 단순 | 적음 |
| **작다** (레코드, 필드) | 칸 하나만 잠금 | ⬆ 높음 | ⬆ 복잡 | 많음 |

> **시험 포인트:** 로킹 단위가 **작아질수록** → 로크 수 ⬆, 관리 복잡 ⬆, **병행성 ⬆**

### 3. 2단계 로킹 규약 (2PL: Two-Phase Locking)
모든 Lock을 먼저 다 걸고(확장 단계), 그 다음에 Unlock을 시작하는(축소 단계) 규칙.

```
[확장 단계(Growing)]     [축소 단계(Shrinking)]
  Lock Lock Lock ...  →  Unlock Unlock Unlock ...
  (잠금만 가능)            (해제만 가능)
```

- 한 번 Unlock을 시작하면 **더 이상 Lock을 걸 수 없다**
- 비유: 마트에서 카트에 물건 담기(Lock) → 계산대 통과 → 물건 내려놓기(Unlock). 계산대 지나면 다시 물건 못 담음!

### 4. 2단계 로킹이 보장하는 것 / 못하는 것

| 구분 | 가능 여부 |
|------|----------|
| **직렬 가능성(Serializability)** 보장 | ⭕ **보장한다** |
| **교착상태(Deadlock)** 예방 | ❌ **예방 못한다** |

#### 직렬 가능성이란?
여러 트랜잭션을 동시에 실행했는데, 결과가 **하나씩 순서대로 실행한 것과 똑같이** 나오는 것.

- 비유: ATM 3대에서 3명이 동시에 송금 → 결과가 1명씩 차례로 한 것과 같다면 = **직렬 가능**

#### 왜 교착상태는 못 막나?
2PL은 "Lock 순서"를 정하지 않기 때문에, 두 트랜잭션이 서로 상대방이 잠근 데이터를 기다리는 상황이 생길 수 있다.

```
T1: A를 Lock → B를 기다림...
T2: B를 Lock → A를 기다림...
→ 둘 다 영원히 기다림 = 교착상태!
```

- 비유: 좁은 골목에서 두 차가 마주보고 멈춤. 둘 다 "네가 비켜" → 아무도 못 움직임
