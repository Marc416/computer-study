데이터링크 제어와 흐름제어

오류 검출·정정, ARQ 재전송 기법, 슬라이딩 윈도우 · PART 03. 데이터통신론

핵심 요약

데이터링크 계층은 오류 검출/정정(패리티·CRC·해밍코드)과 흐름제어(슬라이딩 윈도우), 오류 복구(ARQ)를 담당한다.

패리티·CRC는 오류를 검출만 하고, 해밍코드는 검출 후 직접 정정까지 한다는 게 핵심 차이.

🎯이 단원을 왜 배우나

선로는 생각보다 자주 틀린다

전선이나 전파로 0과 1을 보내면, 전기 잡음·간섭 때문에 보낸 1이 0으로 뒤집혀 도착하는 일이 실제로 일어난다. 문제는 받는 쪽이 그걸 알 방법이 없다는 것이다 — 도착한 비트열만 봐서는 "원래 이랬던 건지, 중간에 망가진 건지" 구분이 안 된다.

그래서 데이터링크 계층은 일부러 군더더기 정보(중복 정보)를 덧붙여 보낸다. 패리티 비트 1개, CRC의 나머지값, 해밍코드의 패리티 비트 여러 개가 전부 그 군더더기다. 받는 쪽은 "덧붙인 규칙이 여전히 맞는지"를 검사해서 오류를 알아낸다. 덧붙이는 정보가 많을수록 더 정밀하게 잡아내지만 그만큼 전송 효율이 떨어진다 — 검출만 할지(패리티·CRC), 위치까지 찾아 고칠지(해밍코드)가 이 트레이드오프의 선택이다.

오류를 발견한 뒤에는 두 갈래다. 다시 보내달라고 요청하거나(ARQ), 받은 쪽이 알아서 고치거나(FEC). 그리고 재전송을 하려면 "어디까지 잘 받았는지" 주고받아야 하는데, 그 관리 도구가 슬라이딩 윈도우다. 이 단원의 모든 내용이 결국 "틀릴 수 있다 → 어떻게 알아채고 → 어떻게 복구할까"라는 한 줄기 이야기다.

패리티 비트 — 가장 단순한 검출

데이터에 비트 딱 1개를 덧붙여, 전체(데이터+패리티)의 1의 개수가 항상 짝수(짝수 패리티) 또는 홀수(홀수 패리티)가 되도록 맞춘다. 받는 쪽은 1의 개수만 세보면 된다.

왜 짝수 개 오류는 못 잡는가 — 패리티의 결정적 한계

비트 1개가 뒤집히면 1의 개수가 하나 늘거나 줄어 홀짝이 반드시 바뀐다 → 검출 성공.

그런데 비트 2개가 동시에 뒤집히면? 하나는 늘고 하나는 줄거나(±0), 둘 다 늘거나(+2), 둘 다 줄어(−2) — 어느 경우든 홀짝이 원래대로 돌아온다 → 검출 실패. 4개, 6개도 마찬가지다.

그래서 정확한 표현은 "단일 패리티는 홀수 개의 비트 오류만 검출할 수 있다"이다. 시험에서 이 문장의 홀수·짝수를 뒤바꿔 놓는 함정이 자주 나온다.

예제. 짝수 패리티를 쓰는 시스템에서 어느 데이터에 오류가 있는가? (데이터 5개 중 3개는 정상, 2개에 오류)

이름데이터 비트열패리티 비트전체 1의 개수판정
A0100110114 + 1 = 5 (홀수)오류
B0111011015 + 1 = 6 (짝수)정상
C1011100004 + 0 = 4 (짝수)정상
D1111000105 + 0 = 5 (홀수)오류
E1010101004 + 0 = 4 (짝수)정상
  1. 각 행의 데이터 비트열 + 패리티 비트를 합쳐 1의 개수를 센다
  2. 정상인 것이 3개(B, C, E)이고 전부 짝수 → 이 시스템은 짝수 패리티를 쓴다고 판명
  3. 규칙을 어긴(홀수인) A와 D가 오류 발생 데이터 → 정답: A, D
요령: 문제에 "짝수 패리티"라고 안 알려줘도 괜찮다. 다수파(정상인 쪽)가 규칙이다. 5개 중 3개가 짝수면 짝수 패리티, 소수파가 오류다.

CRC (순환중복검사) — 실무에서 가장 많이 쓰는 검출법 📖 기출문제집 p.356

  • 송신측: 데이터 끝에 n개의 0을 붙이고, 미리 정한 제수(n+1비트)로 모듈로-2 나눗셈 → 나머지(n비트)를 FCS(프레임 검사 순서)로 원본 데이터 뒤에 붙여 전송
  • 수신측: 받은 전체(데이터+FCS)를 같은 제수로 나눠서 나머지가 0이면 정상, 0이 아니면 오류
  • 다항식 코드를 사용해 집단(burst) 오류 검출에 특히 강함 — 그래서 이더넷·Wi-Fi 등 대부분의 프로토콜이 채택

모듈로-2 나눗셈이란

겁먹을 것 없다. 일반 나눗셈과 똑같은데 뺄셈 대신 XOR을 쓰는 것뿐이다. 자리올림·자리내림이 없어서 계산이 훨씬 쉽다.

  • 0 XOR 0 = 0, 1 XOR 1 = 0, 0 XOR 1 = 1, 1 XOR 0 = 1
  • 맨 앞자리가 1이면 제수로 XOR, 0이면 그냥 다음 비트를 내린다

계산 예제. 데이터 1101, 제수 1011(4비트)일 때 전송할 프레임은?

  1. 제수가 4비트(n+1=4) → n=3이므로 데이터 뒤에 0을 3개 붙인다 → 1101000
  2. 모듈로-2 나눗셈 수행 (아래 표)
  3. 나머지 001이 FCS가 된다
  4. 전송 프레임 = 원본 데이터 + FCS = 1101 + 001 = 1101001
단계현재 값연산결과
11101000XOR 10110110 → 다음 비트 내림 → 1100
21100XOR 10110111 → 다음 비트 내림 → 1110
31110XOR 10110101 → 다음 비트 내림 → 1010
41010XOR 10110001 → 더 내릴 비트 없음 → 나머지 001
검산: 수신측이 1101001을 같은 제수 1011로 나누면 → 1101⊕1011=0110→1100, 1100⊕1011=0111→1110, 1110⊕1011=0101→1011, 1011⊕1011=0000. 나머지가 0이므로 오류 없음으로 판정된다. 계산이 맞았는지 이렇게 확인할 수 있다.

해밍코드 — 위치까지 찾아내 스스로 고친다 📖 기출문제집 p.354~355

패리티 1개로는 "틀렸다"까지만 안다. 해밍코드는 패리티 비트를 여러 개, 그것도 2의 거듭제곱 위치(1, 2, 4, 8...)에 심어서 어느 자리가 틀렸는지 좌표까지 알아낸다. 그래서 재전송 없이 수신측이 혼자 고칠 수 있다(FEC 방식).

실전 예제. 짝수 패리티 해밍코드로 0011111을 수신했다. 오류를 찾아 정정하면?

  1. 값이 1인 자리의 번호를 모두 찾는다 → 3, 4, 5, 6, 7번
  2. 각 번호를 3비트 2진수로 변환: 3=011, 4=100, 5=101, 6=110, 7=111
  3. 전부 비트 단위로 XOR: 011⊕100=111 → ⊕101=010 → ⊕110=100 → ⊕111=011
  4. 011 = 10진수 3 → 3번 자리가 틀렸다는 뜻
  5. 3번 자리를 반전(1 → 0): 0011111 → 0001111
원리 직관: 오류가 없으면 XOR 결과가 반드시 0이 나오도록 패리티를 미리 심어둔 것이다. 그래서 결과가 0이 아니면 그 값 자체가 "몇 번째 비트가 틀렸는지" 알려주는 좌표가 된다. 마치 범인이 자기 주소를 남기고 가는 셈이다.
한계: 해밍코드는 1비트 오류만 정정할 수 있다. 2비트가 동시에 틀리면 엉뚱한 위치를 "고쳐서" 오히려 데이터를 더 망가뜨린다. 또 패리티 비트를 여러 개 붙이므로 전송 효율이 낮고 계산량이 많다.

Go-Back-N 재전송 개수 계산 📖 기출문제집 p.357

계산 방법은 딱 한 줄이다: 재전송 개수 = (마지막으로 보낸 번호) − (오류 난 번호) + 1. 오류 난 것부터 끝까지 전부 다시 보내기 때문이다.

예제: 6번 프레임까지 전송했는데 4번 프레임에서 오류 발견 → 재전송 개수는?

  1. Go-Back-N 규칙: 오류난 프레임부터 이미 보낸 나머지 전부를 다시 보낸다
  2. 오류 지점: 4번. 이미 전송된 마지막: 6번
  3. 재전송 대상: 4번, 5번, 6번 → 6 − 4 + 1 = 총 3개

🪟주요 개념 — 흐름제어: 슬라이딩 윈도우

흐름제어는 왜 필요한가

송신측이 빠르고 수신측이 느리면, 수신측 버퍼가 넘쳐서 도착한 데이터가 그냥 버려진다. 오류가 없었는데도 데이터를 잃는 것이다. 이를 막으려고 "받는 쪽이 감당할 만큼만 보내라"고 속도를 조절하는 것이 흐름제어다.

가장 단순한 방법은 1개 보내고 응답 기다리기(정지-대기)지만 너무 느리다. 그래서 "응답 없이도 미리 N개까지는 보내도 좋다"고 한도를 정한 것이 슬라이딩 윈도우다. 그 한도가 윈도우 크기이고, 응답이 올 때마다 창문이 오른쪽으로 미끄러지듯(sliding) 이동하며 새 프레임을 보낼 여유가 생긴다.

계산/이해 방법: 윈도우는 "응답 없이 한 번에 보낼 수 있는 프레임 개수"의 한도다. 송신측은 보낼 때마다 줄고 ACK 받으면 늘고, 수신측은 받을 때마다 줄고 ACK를 보내면 는다. 방향을 뒤집어 놓는 것이 이 단원 최대의 함정이다.

함정 주의: 시험에 "수신측 윈도우는 프레임을 수신할 때마다 하나씩 늘어나고..."처럼 방향을 뒤바꾼 오답이 자주 나온다. "수신측은 받으면 줄고(자리가 차니까), 응답 보내면 는다(자리를 비웠으니까)"로 이해하면 헷갈리지 않는다.

📌시험 빈출 포인트

  • 해밍코드만 오류 정정 가능, 패리티·CRC·블록합·체크섬은 검출만 가능
  • BCD는 오류 검출 방식이 아니다 (문자 코드 체계) — "검출 방식이 아닌 것" 단골 정답
  • 단일 패리티는 홀수 개 비트 오류만 검출 가능 (짝수 개는 상쇄되어 놓침)
  • CRC는 다항식(모듈로-2 = XOR) 나눗셈, 나머지를 FCS로 첨부, 집단 오류에 강함
  • 해밍코드 오류 위치 = 1인 자리 번호들을 전부 XOR한 값
  • ARQ = 송신측 재전송(후진), FEC = 수신측 자체 정정(전진, 해밍코드)
  • Go-Back-N 재전송 개수 = 마지막 번호 − 오류 번호 + 1
  • 전송 효율: 선택적 재전송 > Go-Back-N > 정지-대기
  • 슬라이딩 윈도우 송신측/수신측 증감 방향 뒤바꾸기 함정 주의

문제 12014 국가직 · 기출문제집 p.351

데이터 전송 중에 발생하는 에러를 검출하는 방식으로 옳지 않은 것은?

  1. 패리티(parity) 검사 방식
  2. 검사합(checksum) 방식
  3. CRC 방식
  4. BCD 부호 방식
해설 보기

정답 ④ BCD 부호 방식

BCD(Binary Coded Decimal)는 숫자·문자를 2진수로 표현하기 위한 코드 체계이지 오류 검출 기법이 아니다. 존(zone) 2비트 + 디지트(digit) 4비트로 64개 문자를 표현한다.

  1. 오류 검출: 패리티 검사, 블록합 검사, CRC, 체크섬
  2. 오류 검출 + 정정: 해밍코드
  3. 코드 체계(검출과 무관): BCD, ASCII, EBCDIC, 유니코드

요령: 선택지에 "~부호", "~코드"처럼 문자 표현 방식 이름이 섞여 있으면 그게 정답일 확률이 높다.

문제 22009 국가직 · 기출문제집 p.353

1비트 패리티 비트로 전송 에러를 검출한다. 1바이트 데이터 A~E 다섯 개를 전송했고 그중 두 개에서 1비트 에러가 발생했다. 에러가 발생한 두 데이터는?

이름데이터 비트열패리티 비트
A010011011
B011101101
C101110000
D111100010
E101010100
  1. A, D
  2. B, C
  3. B, E
  4. C, E
해설 보기

정답 ① A, D

문제가 홀수 패리티인지 짝수 패리티인지 알려주지 않는다. 하지만 정상인 3개가 따르는 규칙이 곧 그 시스템의 규칙이다.

  1. 데이터 + 패리티를 합쳐 1의 개수를 센다:
    A = 4+1 = 5(홀) · B = 5+1 = 6(짝) · C = 4+0 = 4(짝) · D = 5+0 = 5(홀) · E = 4+0 = 4(짝)
  2. 짝수인 것이 B, C, E 3개 → 이 시스템은 짝수 패리티
  3. 규칙을 어긴 홀수짜리 A와 D가 에러 발생 데이터

함정: 1의 개수를 셀 때 패리티 비트까지 포함해야 한다. 데이터 비트만 세면 홀짝이 반대로 나와 정답이 뒤집힌다.

문제 32015 지방직 · 기출문제집 p.355~356

네트워크의 전송 데이터 오류 검출에 대한 설명으로 옳지 않은 것은?

  1. 체크섬(checksum)은 1의 보수 방법을 사용한다.
  2. 순환중복검사(CRC)는 모듈로-2 연산을 주로 사용한다.
  3. 전송할 데이터에 대한 중복 정보를 활용하여 오류를 검출한다.
  4. 단일 패리티 비트를 사용하는 패리티 검사는 홀수 개의 비트에 오류가 발생하면 오류를 발견할 수 없다.
해설 보기

정답 ④ (홀수·짝수가 뒤바뀐 서술)

올바른 서술은 "단일 패리티 검사는 홀수 개 오류는 발견할 수 있고, 짝수 개 오류는 발견할 수 없다"이다.

  1. 비트 1개(홀수) 뒤집힘 → 1의 개수 홀짝이 바뀜 → 검출 성공
  2. 비트 2개(짝수) 뒤집힘 → 홀짝이 원상복구 → 검출 실패
  3. 따라서 ④는 홀수와 짝수를 정확히 반대로 서술한 오답

①②③은 모두 맞는 설명이다. 체크섬은 합을 구해 1의 보수를 취해 붙이고, CRC는 모듈로-2(XOR) 나눗셈을 쓰며, 모든 오류 검출은 중복 정보(redundancy)를 덧붙인다는 공통 원리를 가진다.

문제 42020 지방직 · 기출문제집 p.357

다음에서 설명하는 네트워크 데이터 오류 검출 방법은?

송신측: 첫 비트가 1인 n+1비트의 제수를 정하고, 데이터 끝에 n비트의 0을 추가한 후 모듈로-2 연산을 한다. 그러면 n비트 나머지가 나오는데 이것이 중복 정보가 된다.

수신측: 전송받은 정보를 동일한 n+1비트 제수로 모듈로-2 연산 한다. 나머지가 0이면 오류 없음, 0이 아니면 오류로 간주한다.

  1. 수직 중복 검사(VRC)
  2. 세로 중복 검사(LRC)
  3. 순환 중복 검사(CRC)
  4. 체크섬(Checksum)
해설 보기

정답 ③ 순환 중복 검사(CRC)

지문의 키워드 세 개가 전부 CRC를 가리킨다.

  1. "n+1비트 제수" = 생성 다항식(generator polynomial) → CRC의 핵심 장치
  2. "데이터 뒤에 0을 n개 붙이고 모듈로-2 연산" = CRC의 FCS 생성 절차
  3. "나머지가 0이면 정상" = CRC의 수신측 검증 방식

구분 정리: VRC는 문자마다 세로로 붙이는 단순 패리티, LRC는 블록 단위 가로 패리티(둘을 합치면 블록합 검사), 체크섬은 덧셈 후 1의 보수를 쓴다. "나눗셈/다항식/모듈로-2"가 나오면 무조건 CRC.

문제 52009 지방직 · 기출문제집 p.354

짝수 패리티를 갖는 7비트 데이터 0011111이 수신되었다. 해밍코드를 이용해 전송 중 발생한 오류를 찾아 바르게 정정한 것은?

  1. 0011100
  2. 0011011
  3. 0001111
  4. 0010111
해설 보기

정답 ③ 0001111

  1. 왼쪽부터 1~7번 인덱스를 매기고, 값이 1인 자리를 고른다 → 3, 4, 5, 6, 7번
  2. 각 번호를 3비트 2진수로: 3=011, 4=100, 5=101, 6=110, 7=111
  3. 전부 XOR:
    011 ⊕ 100 = 111
    111 ⊕ 101 = 010
    010 ⊕ 110 = 100
    100 ⊕ 111 = 011
  4. 011 = 3 → 3번 비트에서 오류 발생
  5. 3번 비트를 1 → 0으로 반전: 0011111 → 0001111

검산: 정정 후 1인 자리는 4,5,6,7번 → 100⊕101=001, ⊕110=111, ⊕111=000. XOR 결과가 0이 나오므로 오류 없음 ✅ 이렇게 검산하면 실수를 잡을 수 있다.

문제 62019 국가직 · 기출문제집 p.358

Go-Back-N 프로토콜에서 6번째 프레임까지 전송한 후 4번째 프레임에서 오류가 있음을 알았을 때, 재전송 대상이 되는 프레임의 개수는?

  1. 1개
  2. 2개
  3. 3개
  4. 6개
해설 보기

정답 ③ 3개

  1. Go-Back-N은 오류 난 프레임부터 그 뒤 전부를 재전송한다
  2. 오류 번호 4, 마지막 전송 번호 6
  3. 재전송 대상 = 4, 5, 6번 → 6 − 4 + 1 = 3개

함정: ①(1개)은 선택적 재전송이었다면 맞는 답이다. 문제에 어떤 ARQ인지 반드시 확인할 것. ④(6개)는 처음부터 전부 다시 보낸다고 착각한 경우인데, Go-Back-N은 이미 ACK된 1~3번은 다시 보내지 않는다.

문제 72016 지방직 · 기출문제집 p.358

데이터 링크 계층 오류제어 기법들을 프레임 전송 효율이 좋은 것부터 나쁜 순으로 바르게 나열한 것은? (구현 복잡도·비용은 무시)

ㄱ. 정지 후 대기(stop-and-wait) ARQ  ·  ㄴ. N 복귀(go-back-N) ARQ  ·  ㄷ. 선택적 반복(selective-repeat) ARQ

  1. ㄱ → ㄴ → ㄷ
  2. ㄴ → ㄷ → ㄱ
  3. ㄷ → ㄱ → ㄴ
  4. ㄷ → ㄴ → ㄱ
해설 보기

정답 ④ ㄷ → ㄴ → ㄱ (선택적 반복 > N 복귀 > 정지 후 대기)

  1. 정지 후 대기(ㄱ): 1개 보내고 응답을 기다리는 동안 회선이 논다 → 반이중처럼 동작하므로 효율 최하
  2. N 복귀(ㄴ): 연속 전송은 하지만 오류 시 멀쩡한 프레임까지 재전송하는 낭비 → 중간
  3. 선택적 반복(ㄷ): 연속 전송 + 오류난 것만 재전송 → 낭비가 가장 적음 → 효율 최고

주의: "효율이 높다 = 좋기만 하다"가 아니다. 선택적 반복은 수신측에 재조합 버퍼가 필요하고 구현이 복잡하다. 문제에서 "구현 복잡도는 무시한다"고 단서를 단 이유가 이것이다.

문제 82008 국가직 · 기출문제집 p.359

슬라이딩 윈도우 기법에 대한 설명으로 옳지 않은 것은?

  1. 흐름제어와 에러제어를 위한 기법으로 윈도우 크기만큼의 데이터 프레임을 연속적으로 전송할 수 있다.
  2. 윈도우 크기를 지정하여 응답 없이 전송할 수 있는 데이터 프레임의 최대 개수를 제한할 수 있다.
  3. 송신측 윈도우는 데이터 프레임을 전송할 때마다 하나씩 줄어들고 응답을 받을 때마다 하나씩 늘어난다.
  4. 수신측 윈도우는 데이터 프레임을 수신할 때마다 하나씩 늘어나고 응답을 전송할 때마다 하나씩 줄어든다.
해설 보기

정답 ④ (수신측의 증감 방향이 반대)

올바른 서술은 "수신측 윈도우는 프레임을 수신할 때마다 하나씩 줄어들고, 응답(ACK)을 전송할 때마다 하나씩 늘어난다"이다.

  1. 수신측 윈도우 = "앞으로 더 받을 수 있는 여유 자리"
  2. 프레임이 도착하면 자리가 차므로 줄어든다
  3. 처리 후 ACK를 보내면 그 자리가 비워져 다시 늘어난다

암기법: 송신측이든 수신측이든 "일이 들어오면 줄고, 처리해서 내보내면 는다"로 같은 논리다. 송신은 "보내는 것"이 일이고, 수신은 "받는 것"이 일이라고 생각하면 방향이 헷갈리지 않는다.
