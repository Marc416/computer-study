가상 메모리

페이징·세그멘테이션·페이지 교체 알고리즘·스래싱 · PART 02. 운영체제론

핵심 요약

가상 메모리는 보조기억장치 일부를 주기억장치처럼 사용해, 실제 RAM 용량보다 큰 프로그램도 실행 가능하게 하는 기법.

구현 방법은 페이징(고정 크기)과 세그멘테이션(가변 크기) 두 가지. 페이지 교체가 너무 잦으면 스래싱이 발생한다.

🎯이 단원을 왜 배우나

"RAM 8GB인데 왜 10GB짜리 게임이 돌아가는가"

이 단원은 그 질문에 대한 답이다. 비결은 간단하다 — 프로그램 전체를 메모리에 올리지 않기 때문이다. 게임을 실행해도 지금 이 순간 필요한 건 현재 맵과 캐릭터 데이터뿐이고, 나머지 스테이지 데이터는 디스크에 두었다가 필요해질 때 그때 가져오면(demand paging) 된다.

그러려면 두 가지 장치가 필요하다. 첫째, 프로그램은 "메모리 0번지부터 쭉 있다"고 착각한 채 돌아가야 한다 (프로그래머가 실제 물리 위치를 신경 쓰면 안 되니까) → 그래서 가상 주소를 쓰고, 실행 중에 실제 위치로 바꿔주는 동적 주소 변환(DAT)이 필요하다. 둘째, 메모리가 꽉 찼을 때 누구를 내보낼지 정해야 한다 → 그것이 페이지 교체 알고리즘이다.

시험 관점에서 이 단원은 계산 문제의 보고다. ① 가상주소 → 물리주소 변환 계산, ② 페이지 테이블 크기 계산, ③ 페이지 부재 횟수 세기(가장 자주 출제). 특히 ③번은 알고리즘만 알면 손으로 표를 그려 100% 맞힐 수 있는 문제라서 절대 틀리면 안 되는 구간이다.

마지막으로, 이 편리함에는 대가가 있다. 페이지를 너무 자주 들락날락시키면 정작 일은 안 하고 페이지 나르기만 하는 상태가 되는데, 그게 스래싱이다.

💡주요 개념 — 가상 메모리 기초

가상 메모리란? 📖 기출문제집 p.246

  • 프로세스가 사용하는 가상 주소(Virtual Address)와 실제 물리 주소(Physical Address)를 분리
  • 디스크 공간을 가상의 메모리처럼 활용 → 물리적 메모리 크기 제약 없이 프로그램 실행 가능
  • 가상주소 → 물리주소로 바꾸는 것을 동적 주소 변환(DAT)이라 하며, 프로세스 실행 중에 이루어짐
  • 프로세스 주소공간의 일부만 주기억장치에 있고 나머지는 보조기억장치에 있어도 됨 (전체가 다 올라갈 필요 없음)
  • 인위적 연속성: 가상주소에서 연속된 페이지가 물리 메모리에서도 연속일 필요는 없다 — 프로그램만 연속이라고 믿으면 된다
함정 주의: 가상메모리를 쓰면 프로세서 이용률·다중 프로그래밍은 좋아지지만, 개별 프로그램의 수행 속도(응답시간)는 오히려 느려질 수 있다 — "속도가 향상된다"는 표현은 오답으로 자주 나옴. (디스크 접근이 끼어들기 때문)

페이지 부재(page fault)가 나면 실제로 무슨 일이 벌어지나

CPU가 어떤 주소를 참조했는데 그 페이지가 메모리에 없다 — 이때 벌어지는 일을 순서대로 보면 왜 페이지 부재가 "비싼" 사건인지 이해된다.

  1. MMU가 페이지 테이블을 보니 유효비트가 0(메모리에 없음) → 트랩(trap) 발생, 운영체제로 제어가 넘어감
  2. 현재 프로세스는 대기(blocked) 상태로 전환되고, CPU는 다른 프로세스에게 넘어간다 (문맥 교환 발생)
  3. 운영체제가 디스크에서 해당 페이지를 찾아 빈 프레임에 적재. 빈 프레임이 없으면 교체 알고리즘으로 희생 페이지를 선택해 내보냄
  4. 페이지 테이블을 갱신(유효비트 1, 프레임 번호 기록)
  5. 프로세스를 준비 상태로 되돌리고, 중단됐던 명령어를 처음부터 다시 실행

메모리 접근은 나노초(ns) 단위인데 디스크 접근은 밀리초(ms) 단위 — 약 10만 배 차이다. 그래서 페이지 부재율이 조금만 높아져도 전체 성능이 급락한다. 이것이 스래싱의 원리이기도 하다.

출제 포인트: "페이지 폴트는 문맥 교환을 유발한다" → 맞는 설명이다 (2단계).

페이징 (Paging) vs 세그멘테이션 (Segmentation)

구분페이징세그멘테이션
분할 단위페이지 — 고정 크기세그먼트 — 가변 크기 (논리적 의미 단위)
단편화내부 단편화 발생외부 단편화 발생
주소 구성페이지 번호 + 페이지 오프셋세그먼트 번호 + 변위(offset)
프로그램 의미페이지는 논리적 의미를 갖지 않음세그먼트는 논리적 의미 단위를 가짐 (함수·배열 등)
크기모든 페이지가 동일세그먼트마다 다름
비트 수 계산 예: 페이지 크기가 2,048바이트(2¹¹) → 페이지 오프셋 = 11비트.
가상주소 전체가 32비트라면 → 페이지 번호 = 32 − 11 = 21비트.

왜 오프셋 비트 수 = log₂(페이지 크기) 인가

오프셋은 "페이지 안에서 몇 번째 바이트인가"를 나타낸다. 페이지 크기가 2,048바이트라면 페이지 내 위치는 0번부터 2047번까지 표현할 수 있어야 한다. 2048가지 값을 표현하려면 2¹¹ = 2048이므로 11비트가 필요하다.

나머지 상위 비트는 전부 "몇 번 페이지인가"를 나타내는 데 쓴다. 그래서 페이지번호 비트 = 전체 주소 비트 − 오프셋 비트다. 32비트 주소 체계에 페이지 크기 4KB(2¹²)면 오프셋 12비트, 페이지번호 20비트 → 페이지 개수는 2²⁰개.

페이지 테이블과 TLB 📖 기출문제집 p.246~247

  • 페이지 테이블(Page Table): 페이지 번호 ↔ 프레임 번호를 매핑해주는 표. 프로세스마다 존재
  • TLB(Translation Lookaside Buffer): 최근 사용한 페이지↔프레임 변환 결과를 저장해두는 일종의 캐시. 페이지 테이블을 매번 읽는 시간을 줄여 속도 향상
  • 역페이지테이블(Inverted Page Table): 가상 페이지 번호 대신 물리 프레임 기준으로 테이블을 구성 → 테이블 크기가 가상주소 공간이 아닌 실제 메모리 크기에 비례해 작아짐 (단, 탐색 성능 저하 가능 → TLB·해시로 보완)
TLB 관련 함정: "TLB 실패(miss)가 발생할 때마다 페이지 부재가 발생한다" → 틀림. TLB에 없어도 페이지 테이블에는 있을 수 있다(그러면 그냥 조금 느리게 접근할 뿐). 페이지 부재는 페이지 테이블에도 없을 때(디스크에 있을 때) 발생한다. TLB miss ≠ page fault.

계산 방법: 논리주소를 페이지 크기로 나눈 몫이 페이지번호, 나머지가 변위(offset)다. 페이지테이블에서 그 페이지번호에 해당하는 프레임번호를 찾은 뒤, 프레임번호×페이지크기 + 변위로 물리주소를 만든다.

물리주소 계산 예제: 페이지 크기 2,000byte, 논리주소 2500 📖 기출문제집 p.248
  1. 페이지 번호 = 논리주소 ÷ 페이지크기 = 2500 ÷ 2000 = 1 (몫)
  2. 변위(offset) = 논리주소 % 페이지크기 = 2500 % 2000 = 500 (나머지)
  3. 페이지 테이블에서 "1번 페이지 → 3번 프레임" 매핑을 확인
  4. 물리주소 = 프레임번호 × 페이지크기 + 변위 = 3 × 2000 + 500 = 6500
주의: 변위(500)는 절대 바뀌지 않는다. 페이지 안에서의 상대 위치는 그대로이고, 페이지가 통째로 어느 프레임에 놓였는지만 달라지기 때문이다.
페이지 테이블 크기 계산 예제 (2016 서울시): 페이지 크기 2KB, 테이블 항목 1개당 3바이트, 프로세스 크기 25KB 📖 기출문제집 p.247
  1. 필요한 페이지 개수 = 프로세스 크기 ÷ 페이지 크기 = 25KB ÷ 2KB = 12.5 → 올림해서 13개 (0.5페이지도 한 페이지를 차지)
  2. 페이지 테이블 크기 = 페이지 개수 × 항목 크기 = 13 × 3바이트 = 39바이트
핵심: 나누어떨어지지 않으면 반드시 올림한다. 12.5개를 12개로 내리면 나머지 0.5페이지를 매핑할 방법이 없다.
페이지 크기의 트레이드오프 (자주 출제): 페이지 크기가 작아지면 → 관리할 페이지 개수가 늘어 페이지 테이블이 커지고, 대신 내부 단편화는 줄어든다. 페이지 크기가 커지면 → 테이블은 작아지지만 내부 단편화가 커지고, 당장 안 쓸 데이터까지 딸려 올라올 확률이 높아진다. "페이지가 작아지면 테이블도 작아진다"는 대표적 오답이다.

🔄주요 개념 — 페이지 교체 알고리즘

알고리즘교체 기준한 줄 요약
FIFO가장 먼저 적재된(가장 오래된) 페이지 교체들어온 순서대로 내보냄
LRU (Least Recently Used)가장 오랫동안 참조되지 않은 페이지 교체가장 옛날에 쓴 것을 내보냄
LFU (Least Frequently Used)사용 빈도(횟수)가 가장 적은 페이지 교체가장 적게 쓴 것을 내보냄
MFU (Most Frequently Used)사용 빈도가 가장 많은 페이지 교체LFU의 반대
최적 교체 (Optimal)앞으로 가장 오랫동안 사용되지 않을 페이지 교체미래를 봄 (이론상 최선, 구현 불가)
2차 기회 (Second-chance)FIFO 기반 + 참조비트. 참조비트가 1이면 0으로 바꾸고 한 번 더 기회, 참조비트가 0인 페이지만 교체 대상FIFO에 관용을 더함
구분 요령: LRU는 "언제" 썼는지(시점)를 보고, LFU는 "몇 번" 썼는지(횟수)를 본다. 이름에 Recently(최근)가 있으면 시점, Frequently(빈번)가 있으면 횟수다.

페이지 부재 횟수 세기 — 손으로 푸는 표준 절차

이 유형은 표를 그리면 무조건 맞힌다. 암산하려다 틀리는 경우가 대부분이므로 아래 순서를 그대로 따를 것.

  1. 세로로 프레임 개수만큼 칸을 그리고, 가로로 참조열을 늘어놓는다.
  2. 참조를 하나씩 보며 "지금 프레임 안에 있나?"만 확인 → 있으면 적중(hit), 없으면 부재(fault).
  3. 부재인데 빈 칸이 있으면 그냥 채운다 (교체 아님 — 처음 채우는 단계).
  4. 부재인데 꽉 찼으면 알고리즘 기준으로 희생자를 골라 빼고 넣는다 (= 교체 발생).
  5. 부재가 발생한 칸에 V 표시를 하고, 마지막에 V 개수를 센다.

주의 1: 문제가 "페이지 부재 횟수"를 묻는지 "페이지 교체 횟수"를 묻는지 구분하라. 교체 횟수 = 부재 횟수 − 처음 프레임을 채운 횟수다 (프레임이 n개면 보통 부재 − n).

주의 2: LRU는 적중했을 때도 사용 순서를 갱신해야 한다. 이걸 빼먹으면 뒤에서 엉뚱한 페이지를 내보내게 된다.

계산 예제 ① LRU — 참조열 "2 1 2 3 1 4 5 1 4 3", 프레임 3개 📖 기출문제집 p.259

  2. 1 → 없음 → 부재, [2,1]
  3. 2 → 있음 → 적중, 사용순서 갱신 [1,2]
  4. 3 → 없음, 자리 있음 → 부재, [1,2,3]
  5. 1 → 있음 → 적중, 갱신 [2,3,1]

계산 예제 ③ LRU 최악의 경우 — 참조열 "1,2,3"×4회 + "4,5,6,7"×3회, 프레임 3개 📖 기출문제집 p.256~257
  1. 앞부분(1,2,3 반복 12회): 처음 1·2·3에서 부재 3회. 이후 프레임에 1,2,3이 다 있으므로 계속 적중 → 부재 3회
  2. 뒷부분(4,5,6,7 반복 12회): 프레임은 3개인데 4개 페이지를 돌려가며 참조한다. 방금 내보낸 페이지를 바로 다음에 다시 요구하는 상황이 반복 → 12회 전부 부재
  3. 총 부재 = 3 + 12 = 15회
교훈: 순환 참조 패턴의 주기가 프레임 개수보다 크면 LRU는 매번 "직전에 버린 것"을 다시 요구하게 되어 적중률이 0이 된다. 프레임이 하나만 더 있었다면(4개) 뒷부분도 전부 적중했을 것이다.
벨레이디의 변칙 (Belady's Anomaly): FIFO는 페이지 프레임 개수를 늘렸는데도 오히려 페이지 폴트가 증가하는 역설적 현상이 발생할 수 있다. (LRU·최적 교체에서는 발생하지 않음) — 시험에서 "LRU에서 벨레이디 변칙이 발생한다"고 쓰면 오답이다.

🔥주요 개념 — 지역성·스래싱·작업집합

지역성 (Locality)

프로세스가 실행되는 동안 메모리의 일부분만 집중적으로 참조하는 경향. 배열을 순서대로 순회하는 것은 공간 지역성의 대표 예.

지역성이 없다면 가상 메모리는 성립하지 않는다

가상 메모리의 전제는 "프로그램 전체를 올리지 않아도 대부분의 참조가 이미 올라온 페이지에서 해결된다"는 것이다. 만약 프로그램이 메모리 전체를 무작위로 참조한다면 페이지 부재가 끊임없이 발생해 가상 메모리는 쓸모없어진다.

  • 시간 지역성(temporal): 최근 참조한 것을 또 참조 — 반복문의 제어 변수, 자주 호출되는 함수
  • 공간 지역성(spatial): 참조한 것의 근처를 참조 — 배열 순회, 순차적 코드 실행

그래서 지역성이 좋은 프로그램일수록 적은 프레임으로도 잘 돌아가고, 지역성이 나쁘면 스래싱에 쉽게 빠진다.

스래싱 (Thrashing)

  • 페이지 부재가 너무 자주 일어나 프로그램 실행 시간보다 페이지 교체 시간이 더 커지는 현상
  • 다중 프로그래밍의 정도(동시 실행 프로세스 수)가 높아질수록 스래싱 발생 가능성 ↑
  • 스래싱이 시작되면 CPU 이용률은 급격히 떨어진다 (다중 프로그래밍 정도를 높인다고 CPU 이용률이 계속 올라가는 것이 아님)
  • 해결책: 다중 프로그래밍의 정도를 낮추기 (프로세스 일부를 중단시켜 페이지 프레임 여유 확보)
함정 주의: "다중 프로그래밍 정도가 높아짐에 따라 CPU 이용률이 계속 높아진다"는 틀린 설명 — 어느 지점을 넘으면 스래싱으로 급락한다 (역 U자 곡선). 또한 스래싱 해결책은 다중 프로그래밍 정도를 낮추는 것이지 높이는 것이 아니다.

작업 집합 (Working Set)

프로세스가 일정 시간 범위 내에 자주 참조하는 페이지들의 집합. 프로세스 실행 중 참조 지역성이 이동하면서 작업 집합도 계속 변한다 (한 번 정해지면 고정되는 것이 아님).

비유: 시험공부를 할 때 책상 위에 올려두는 책들. 지금 수학을 공부하면 수학책·문제집·연습장이 작업 집합이고, 영어로 넘어가면 책상 위 구성이 통째로 바뀐다. 운영체제는 각 프로세스에게 "지금 책상에 필요한 만큼"의 프레임을 주려고 한다 — 그보다 적게 주면 계속 책을 들락날락시켜야 하니 스래싱이다.

페이지 부재 빈도 기법 (Page Fault Frequency)

프로세스의 페이지 부재율을 감시해서, 부재율이 설정한 상한을 넘으면 프레임을 더 주고, 하한보다 낮으면 프레임을 회수하는 방식으로 스래싱을 조절하는 기법. 작업 집합을 직접 추적하지 않고 결과(부재율)만 보고 조절한다는 점이 작업집합 기법과 다르다.

📌시험 빈출 포인트

  • 가상메모리는 응답시간을 느리게 만들 수 있음 (속도 향상 아님)
  • 동적 주소 변환(DAT)은 프로세스 실행 중에 이루어짐
  • 페이징=내부단편화만, 세그멘테이션=외부단편화만 발생
  • 페이지 크기가 작아지면 페이지 테이블 크기는 커진다 (관리할 페이지 개수 증가)
  • 페이지 테이블 크기 = 올림(프로세스크기÷페이지크기) × 항목크기
  • TLB는 페이지 테이블의 캐시 역할 / TLB miss ≠ page fault
  • 역페이지테이블은 테이블 크기가 실제 메모리 크기에 비례 (가상주소공간 크기와 무관)
  • FIFO만 벨레이디의 변칙 발생 가능 (프레임 늘렸는데 폴트 증가)
  • 페이지 부재 횟수 vs 페이지 교체 횟수 구분 (교체 = 부재 − 초기 적재분)
  • 스래싱 = 페이지 교체시간 > 프로그램 실행시간, 해결은 다중프로그래밍 정도를 낮추는 것
  • 작업 집합은 고정되지 않고 계속 변함 (오답 함정으로 자주 출제)
  • 페이지 교체 알고리즘별 폴트 횟수 계산 문제 (FIFO/LRU/LFU/Optimal 비교) 거의 매년 출제

LRU 교체 기법을 사용하는 요구 페이징 시스템에서 3개의 페이지 프레임을 할당받은 프로세스가 다음 순서로 페이지에 접근할 때 발생하는 페이지 부재 횟수는? (프레임은 초기에 모두 비어 있음)
1,2,3, 1,2,3, 1,2,3, 1,2,3, 4,5,6,7, 4,5,6,7, 4,5,6,7

  1. 7번
  2. 10번
  3. 14번
  4. 15번
해설 보기

정답 ④ 15번

참조열이 24개나 되지만, 두 구간으로 나누면 표를 다 그리지 않아도 된다.

  1. 앞 구간 (1,2,3 × 4회 = 12개 참조): 맨 처음 1, 2, 3에서 각각 부재 → 프레임 = {1,2,3}. 이후로는 요구하는 페이지가 항상 프레임 안에 있으므로 전부 적중 → 부재 3회
  2. 뒤 구간 (4,5,6,7 × 3회 = 12개 참조): 프레임은 3개인데 4개의 페이지를 순환하며 요구한다.
  3. 4 요구 → 가장 오래 안 쓴 1 제거 → {2,3,4} / 5 요구 → 2 제거 → {3,4,5} / 6 요구 → 3 제거 → {4,5,6} / 7 요구 → 4 제거 → {5,6,7}
  4. 그런데 다음 요구가 다시 4다 — 방금 내보낸 페이지를 바로 다시 부른다. 이 패턴이 끝까지 반복 → 12회 전부 부재
  5. 총 부재 = 3 + 12 = 15회

이 문제가 가르치는 것: LRU는 순환 참조의 주기(4)가 프레임 수(3)보다 크면 적중률이 0이 된다. 프레임이 하나만 더 있었다면(4개) 뒤 구간도 첫 4회만 부재였을 것이다. 프레임 수와 작업집합 크기의 관계를 보여주는 대표 문제다.

문제 52016 서울시 · 기출문제집 p.247

메모리 크기가 200KB인 시스템에서 요구 페이징으로 가상 메모리를 구현한다. 페이지 크기가 2KB이고 페이지 테이블의 각 항목이 3바이트일 때, 25KB 크기의 프로세스를 위한 최소 페이지 테이블의 크기는?

  1. 25바이트
  2. 39바이트
  3. 60바이트
  4. 75바이트
해설 보기

정답 ② 39바이트

  1. 프로세스가 차지하는 페이지 개수 = 25KB ÷ 2KB = 12.5 → 올림하여 13개
  2. 페이지 테이블은 페이지 1개당 항목 1개를 가진다 → 항목 13개
  3. 테이블 크기 = 13 × 3바이트 = 39바이트

함정 ①: 12.5를 12로 내림하면 36바이트가 되어 오답. 남는 0.5페이지도 반드시 한 페이지를 차지하므로 올림이다.

함정 ②: 문제에 나온 "메모리 크기 200KB"는 이 계산에 쓰이지 않는 정보다. 페이지 테이블 크기는 프로세스 크기로 결정되지 전체 메모리 크기와 무관하다. 이렇게 안 쓰는 숫자를 섞어 넣는 것도 출제 기법이다.

문제 62012 국가직 · 기출문제집 p.247

페이징 기법에서 페이지 크기에 대한 설명으로 옳지 않은 것은?

  1. 페이지 크기가 작아지면 페이지 테이블의 크기도 줄어든다.
  2. 주기억장치는 페이지와 같은 크기의 블록으로 나누어 사용된다.
  3. 페이지 크기가 커지면 내부 단편화되는 공간이 커진다.
  4. 페이지 크기가 커지면 참조되지 않는 불필요한 데이터들이 주기억장치에 적재될 확률이 높아진다.
해설 보기

정답 ① (페이지가 작아지면 테이블은 커진다)

  1. 같은 크기의 프로세스를 더 잘게 쪼개면 페이지 개수가 늘어난다.
  2. 페이지 테이블은 페이지 1개당 항목 1개이므로, 페이지 개수가 늘면 테이블도 커진다.
  3. 예: 100KB 프로세스를 4KB 페이지로 나누면 25개, 1KB 페이지로 나누면 100개 → 테이블 항목이 4배

트레이드오프 정리 (통째로 외우면 유리):

페이지 크기페이지 테이블내부 단편화불필요 데이터 적재
작게커짐 ✗작아짐 ✔적어짐 ✔
크게작아짐 ✔커짐 ✗많아짐 ✗

③·④는 "페이지가 커질 때"의 단점을 정확히 서술한 맞는 설명이다.

문제 72018 국회직 · 기출문제집 p.251~252

가상 메모리 시스템의 페이지 교체 기법에 대한 설명으로 옳지 않은 것은?

  1. LRU 기법은 메모리에 적재된 페이지 중 가장 오랫동안 참조되지 않았던 페이지를 교체하는 기법이다.
  2. LRU 기법은 구현 오버헤드가 커서 일반적으로 LRU 근사 알고리즘들이 사용되는 것이 보통이다.
  3. LRU 기법은 물리적 페이지의 개수를 확장했음에도 페이지 폴트가 늘어나는 경우가 발생할 수 있는데, 이를 Belady's anomaly라 한다.
  4. 이론적으로 최적의 페이지 교체 기법은 앞으로 가장 오랫동안 참조되지 않을 페이지를 교체하는 것이다.
해설 보기

정답 ③ (벨레이디 변칙은 FIFO에서 발생)

  1. 벨레이디의 변칙 = 프레임을 늘렸는데 오히려 페이지 폴트가 증가하는 역설.
  2. 이 현상은 FIFO에서 발생한다. LRU와 최적(Optimal)은 스택 알고리즘이라 불리는 성질을 만족해서 이런 역설이 생기지 않는다.
  3. 스택 알고리즘 성질이란: 프레임이 n개일 때 메모리에 있는 페이지 집합이, 프레임이 n+1개일 때의 집합에 항상 포함된다는 것. 그러니 프레임을 늘렸는데 없던 폴트가 생길 수 없다.

암기: "벨레이디 = FIFO" — F로 시작하는 것끼리 묶어서 외우면 헷갈리지 않는다.

문제 82024 지방직 · 기출문제집 p.246

페이지 테이블을 사용하는 가상기억장치 시스템에서 TLB에 대한 설명으로 옳은 것은?

  1. 페이지 테이블의 캐시로서 동작한다.
  2. 한 시스템 내에 여러 개가 존재할 수 없다.
  3. TLB 실패(miss)가 발생할 때마다 페이지 부재(page fault)가 발생한다.
  4. 물리 주소를 가상 주소로 빠르게 변환하기 위한 것이다.
해설 보기

정답 ①

  1. ① 맞음: TLB는 최근 사용한 (페이지번호 → 프레임번호) 쌍을 담아두는 주소변환 전용 캐시다.
  2. ③ 틀림: TLB에 없어도 페이지 테이블에는 있을 수 있다. 그러면 테이블을 한 번 더 읽어 처리할 뿐 페이지 부재가 아니다. 페이지 부재는 페이지가 메모리 자체에 없을 때 발생한다.
  3. ④ 틀림: 방향이 반대다. 가상 주소 → 물리 주소 변환을 빠르게 하는 것이 목적이다.
  4. ② 틀림: 멀티코어 시스템은 코어마다 TLB를 두고, 명령어용·데이터용을 분리하기도 한다.

비용 감각: TLB 적중 → 수 ns / TLB miss(테이블 조회) → 수십~수백 ns / page fault(디스크) → 수 ms. 세 단계의 비용 차이가 어마어마하다는 것이 ③을 틀린 설명으로 만드는 핵심이다.

문제 92016 국회직 · 기출문제집 p.246

가상기억장치에 대한 설명으로 옳은 것은?

  1. 프로세스의 주소공간 전체가 주기억장치에 적재된다.
  2. 실행 중인 프로세스들에 필요한 전체 주소공간 크기의 합은 주기억장치 용량보다 클 수 없다.
  3. 프로세스에서 사용되는 가상주소의 순서와 주기억장치의 물리주소 순서는 일치한다.
  4. 가상주소를 물리주소로 변환하는 것은 프로세스의 실행 중에 이루어진다.
해설 보기

정답 ④ (동적 주소 변환, DAT)

  1. ① 틀림: 가상 메모리의 핵심은 일부만 올리고 나머지는 디스크에 두는 것이다. 전체 적재가 필요하다면 가상 메모리를 쓸 이유가 없다.
  2. ② 틀림: 정확히 그 반대가 가상 메모리의 존재 이유다 — 주기억장치보다 큰 프로그램도 실행 가능하다.
  3. ③ 틀림: 가상주소에서 연속인 페이지들이 물리적으로 흩어져 있어도 된다. 이를 인위적 연속성(artificial contiguity)이라 한다.
  4. ④ 맞음: 변환은 실행 시점에 매번 MMU가 수행한다. 컴파일·적재 시점에 미리 고정하는 것이 아니다 → 동적 주소 변환.

선택지 읽는 요령: ①②③은 모두 "가상 메모리가 없던 시절의 제약"을 서술하고 있다. 가상 메모리는 그 제약을 깨려고 만든 기술이므로, 제약을 긍정하는 선택지는 대체로 오답이다.

문제 10개념 확인 · 응용

32비트 가상주소 체계에서 페이지 크기가 4KB일 때, ① 오프셋 비트 수, ② 페이지 번호 비트 수, ③ 한 프로세스가 가질 수 있는 최대 페이지 개수는?

해설 보기

정답: ① 12비트 ② 20비트 ③ 2²⁰개(약 100만 개)

  1. 오프셋: 페이지 안의 위치를 가리켜야 하므로 페이지 크기만큼의 값을 표현해야 한다. 4KB = 4,096 = 2¹² → 12비트
  2. 페이지 번호: 남은 상위 비트 전부 = 32 − 12 = 20비트
  3. 최대 페이지 개수: 20비트로 표현 가능한 값의 수 = 2²⁰ = 1,048,576개
  4. 검산: 2²⁰개 × 4KB = 2²⁰ × 2¹² = 2³² = 4GB → 32비트 주소 공간 전체와 일치 ✔

일반화: 주소 비트가 n, 페이지 크기가 2ᵏ 바이트라면 → 오프셋 k비트, 페이지번호 n−k비트, 최대 페이지 2^(n−k)개. 마지막에 "페이지 개수 × 페이지 크기 = 전체 주소공간"으로 검산하는 습관을 들이면 실수를 잡을 수 있다.
