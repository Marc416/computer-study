프로세스 스케줄링

CPU를 어떤 프로세스에 언제 줄지 결정하는 방식 · PART 02. 운영체제론

핵심 요약

비선점(Non-preemptive) = FCFS, SJF, HRN — 한 번 CPU를 잡으면 끝날 때까지 안 뺏김

선점(Preemptive) = RR, SRT, MLQ, MFQ — 더 급한 프로세스가 오면 중간에 CPU를 뺏을 수 있음

🎯이 단원을 왜 배우나

은행 창구 하나에 손님 열 명 — 누구부터 부를 것인가

CPU는 창구 하나, 프로세스는 줄 선 손님이다. 누구를 먼저 부를지에 정답은 없다. 온 순서대로 부르면 공평하지만(FCFS), 앞사람이 한 시간짜리 업무면 뒤의 1분짜리 손님들이 다 같이 한 시간을 버린다. 그렇다고 짧은 일부터 부르면(SJF) 전체 평균 대기는 줄지만 긴 업무를 가진 손님은 영원히 못 부를 수도 있다(기아 상태).

이 단원의 알고리즘들은 전부 이 딜레마를 어떻게 타협했는가의 목록이다. RR은 "각자 3분씩만 하고 다시 줄 서세요"로 공평성을 챙기고, HRN은 "오래 기다린 사람에게 가산점"으로 기아를 막고, MFQ는 "업무 성격에 따라 창구를 나눈다".

시험 대비 관점에서 이 단원은 PART 02에서 배점이 가장 큰 곳이다. 문제 유형은 딱 둘이다 — ① 선점/비선점 분류(암기 1분이면 끝), ② 평균 대기시간·반환시간 계산(간트차트만 정확히 그리면 끝). 아래 계산 규칙 하나만 확실히 익히면 계산 문제는 전부 같은 방식으로 풀린다.

💡주요 개념

스케줄링 평가 기준

기준의미
처리량 (Throughput)단위 시간당 완료되는 프로세스 수 — 클수록 좋음
대기 시간 (Waiting Time)준비 큐에서 CPU를 기다린 시간 — 작을수록 좋음
반환 시간 (Turnaround Time)도착부터 완료까지 전체 시간 (대기시간+실행시간) — 작을수록 좋음
응답 시간 (Response Time)도착부터 반응이 오기까지의 시간 (문제에서 정의를 따로 주는 경우가 많음)
CPU 이용률CPU가 놀지 않고 일한 시간의 비율 — 클수록 좋음

계산 문제의 90%는 이 세 줄로 끝난다

계산 문제에서 공식을 외울 필요는 없다. 간트차트를 그린 다음 아래 세 줄만 적용하면 된다.

  • 반환시간 = 완료시각 − 도착시각 (그 프로세스가 시스템에 머문 총 시간)
  • 대기시간 = 반환시간 − 실행시간 (머문 시간 중 실제로 일 안 하고 기다린 시간)
  • 평균 = 전부 더해서 프로세스 개수로 나눈다

가장 흔한 실수는 도착시각을 빼지 않는 것이다. P2가 t=2에 도착해서 t=9에 끝났다면 반환시간은 9가 아니라 7이다. 늦게 온 손님은 그 전까지 은행에 없었으니 기다린 게 아니다.

주의: "응답시간"은 문제마다 정의가 다르다. 대부분의 공무원 기출은 "도착시간부터 처리가 종료될 때까지"라고 문제 안에 정의를 써 준다 — 이 경우 사실상 반환시간과 같은 값이다. 단서를 반드시 읽자.

선점 vs 비선점 분류 ⭐ (매년 출제) 📖 기출문제집 p.202~203

구분알고리즘의미
비선점 (Non-preemptive)FCFS, SJF, HRN(HRRN)한 번 CPU를 준 이상 스스로 내려올 때까지 못 뺏음
선점 (Preemptive)RR, SRT(=선점 SJF), MLQ, MFQ더 급한 프로세스가 오거나 시간이 다 되면 강제로 회수
암기법: "에프 에스 에이치(F·S·H)는 안 뺏는다" — FCFS, SJF, HRN 세 개만 비선점이고 나머지는 전부 선점이다. 헷갈리는 건 SRT인데, 이름이 SJF와 비슷해도 선점이라는 것만 따로 기억하면 된다.
함정 주의: "RR은 비선점 방식이다" → ❌ RR은 대표적인 선점형이다. "HRN은 선점형이다" → ❌ HRN은 비선점이다(2021 국회직 정답).

FCFS (First Come First Served) 📖 기출문제집 p.209~210

  • 도착한 순서대로 CPU를 할당하는 가장 단순한 비선점 방식
  • 구현이 쉽고 기아상태가 없다(언젠가는 반드시 차례가 옴)
  • 단점: 실행시간이 긴 프로세스가 먼저 오면 뒤 프로세스들이 다 같이 오래 기다림 → 호위 효과(convoy effect)
  • 일괄처리 시스템에는 효율적이나, 빠른 응답이 필요한 대화식 시스템에는 부적합

계산 예제 (2018 계리직): P1(도착0, 처리2) P2(도착2, 처리2) P3(도착3, 처리3) P4(도착4, 처리9)

단계별 풀이 (응답시간 = 도착~완료로 정의된 경우)
  1. P1: 0에 도착, 0~2 실행, 완료 2 → 2 − 0 = 2초
  2. P2: 2에 도착, 2~4 실행, 완료 4 → 4 − 2 = 2초
  3. P3: 3에 도착했지만 P2가 끝나는 4까지 대기, 4~7 실행, 완료 7 → 7 − 3 = 4초
  4. P4: 4에 도착, 7까지 대기, 7~16 실행, 완료 16 → 16 − 4 = 12초
  5. 평균 = (2 + 2 + 4 + 12) ÷ 4 = 20 ÷ 4 = 5초

SJF (Shortest Job First) 📖 기출문제집 p.210

  • 실행시간이 가장 짧은 작업부터 처리하는 비선점 방식 → 평균 대기시간이 이론상 최소
  • 단점: 실행시간이 긴 프로세스는 짧은 것들에 계속 밀려 기아상태(Starvation)에 빠질 수 있음
  • 또 하나의 현실적 문제: "실행시간을 미리 알아야" 한다는 전제가 비현실적이다 (실제로는 과거 이력으로 예측)

계산 예제 (2014 서울시): P1(0,6) P2(1,4) P3(2,1) P4(3,2) — 평균 대기시간은?

단계별 풀이 (대기시간 = 실행 시작 − 도착)
  1. t=0에는 P1만 있으므로 선택의 여지 없이 P1 실행 (0~6). P1 대기 = 0 − 0 = 0
  2. t=6 시점에 P2(4), P3(1), P4(2)가 모두 도착해 있다 → 가장 짧은 P3 선택, 6~7 실행. P3 대기 = 6 − 2 = 4
  3. t=7: 남은 P2(4), P4(2) 중 짧은 P4 선택, 7~9 실행. P4 대기 = 7 − 3 = 4
  4. t=9: 마지막 P2 실행, 9~13. P2 대기 = 9 − 1 = 8
  5. 평균 대기시간 = (0 + 4 + 4 + 8) ÷ 4 = 16 ÷ 4 = 4초

SRT (Shortest Remaining Time) — SJF의 선점 버전 📖 기출문제집 p.219~220

  • SJF와 기준(짧은 것 우선)은 같지만, 새 프로세스가 도착할 때마다 "현재 실행 중인 것의 남은 시간"과 "새로 온 것의 실행시간"을 비교해 더 짧은 쪽에게 CPU를 준다
  • 이론상 평균 대기시간이 가장 짧지만, 선점이 잦아 문맥교환 오버헤드가 크다 → 실제로는 SJF가 더 나을 수도 있다

계산 예제 (2015 국가직): P1(0,8) P2(2,4) P3(4,1) P4(6,4) — 평균 반환시간은?

단계별 풀이 — "도착 시점마다 비교"만 반복하면 된다
  1. t=0: P1만 있음 → P1 실행 시작
  2. t=2: P2(4) 도착. P1 남은 시간 6 vs P2 4 → 짧은 P2가 선점
  3. t=4: P3(1) 도착. P2 남은 2 vs P3 1 → 짧은 P3가 선점
  4. t=5: P3 완료. 남은 것 중 P1(6) vs P2(2) → 짧은 P2 재개
  5. t=6: P4(4) 도착. P2 남은 1 vs P4 4 → P2가 더 짧으므로 계속 실행, t=7에 완료
  6. t=7: P1(6) vs P4(4) → P4 실행, 7~11에 완료
  7. t=11: 마지막 남은 P1이 6초 실행 → 17에 완료
  8. 반환시간 = 완료 − 도착: P1 = 17−0 = 17, P2 = 7−2 = 5, P3 = 5−4 = 1, P4 = 11−6 = 5
  9. 평균 = (17 + 5 + 1 + 5) ÷ 4 = 28 ÷ 4 = 7초

RR (Round Robin) 📖 기출문제집 p.214~215

  • 각 프로세스에게 동일한 시간 할당량(Time Slice/Quantum)만큼만 CPU를 주고, 다 쓰면 강제로 준비 큐 맨 뒤로 보냄
  • 대표적인 선점 방식, 시분할 시스템에 적합
  • Time Slice가 너무 크면 → 아무도 안 잘리므로 사실상 FCFS와 동일해짐
  • Time Slice가 너무 작으면 → 문맥교환(Context Switching)이 잦아져 오버헤드 증가
  • 돌아가며 실행하므로 기아상태가 발생하지 않음

계산 방법: Quantum만큼 실행하다 다 못 끝내면 준비 큐 맨 뒤에 다시 줄을 세운다. 이때 "그 시각에 이미 큐에 있던 프로세스가 먼저"이므로, 시간 순서대로 큐 상태를 적어가며 따라가는 것이 실수를 막는 유일한 방법이다.

계산 예제 (2016 계리직, Quantum=2): P1(도착0,실행3) P2(도착1,실행4) P3(도착3,실행2)
  1. t=0: P1 도착 → 준비큐가 비어있으므로 즉시 CPU 할당, 2초 실행(0~2)
  2. t=1: P2 도착 → 준비큐에서 대기 [P2]
  3. t=2: P1의 Quantum 소진, 잔여 1초 → 준비큐 맨 뒤로 [P1(1)]. 큐 맨 앞 P2가 CPU 할당, 2초 실행(2~4)
  4. t=3: P3 도착 → 준비큐 맨 뒤에 추가 [P1(1), P3]
  5. t=4: P2의 Quantum 소진, 잔여 2초 → 맨 뒤로 [P1(1), P3, P2(2)]. 큐 맨 앞 P1이 남은 1초 실행(4~5) → P1 완료(t=5)
  6. t=5: 큐 맨 앞 P3가 2초 실행(5~7) → P3 완료(t=7)
  7. t=7: 남은 P2가 2초 실행(7~9) → P2 완료(t=9)
  8. 응답시간(도착~종료): P1 = 5−0 = 5, P2 = 9−1 = 8, P3 = 7−3 = 4 → 평균 = 17 ÷ 3 ≈ 5.7초

우선순위(Priority) 스케줄링

  • 프로세스의 상대적 중요도(우선순위)가 높은 것부터 CPU 할당
  • 선점/비선점 둘 다 구현 가능 (선점 방식으로만 되는 것 아님 — 자주 나오는 오답 함정)
  • 우선순위가 낮은 프로세스는 계속 밀려 기아상태 위험
  • 해결책: 노화(Aging) 기법 — 오래 기다린 프로세스의 우선순위를 점점 높여줌

HRN / HRRN (Highest Response-ratio Next) 📖 기출문제집 p.208~209

SJF의 단점(긴 작업의 기아상태)을 보완한 비선점 방식. 대기시간이 길수록 우선순위가 올라가도록 만든 공식을 사용한다.

우선순위 공식: (대기시간 + 서비스시간) ÷ 서비스시간 → 값이 클수록 먼저 처리

이 공식이 왜 기아를 막는가

공식을 1 + (대기시간 ÷ 서비스시간)으로 바꿔 쓰면 의미가 분명해진다. 앞의 1은 모두에게 공통이므로, 실제 순위를 가르는 건 "대기시간 ÷ 서비스시간" 한 덩어리다.

  • 서비스시간이 짧을수록 분모가 작아져 값이 커진다 → SJF의 장점(짧은 작업 우대)을 그대로 유지
  • 대기시간이 길어질수록 분자가 커져 값이 커진다 → 오래 기다리면 결국 순위가 올라간다

즉 긴 작업이라도 기다리는 시간이 쌓이면 언젠가는 1등이 된다. SJF에서는 영원히 밀릴 수 있었던 것이 HRN에서는 불가능해지는 이유다.

MLQ / MFQ (다단계 큐 / 다단계 피드백 큐)

구분설명
MLQ (Multilevel Queue)준비 큐를 우선순위별로 여러 개로 나누고, 각 큐마다 서로 다른 스케줄링 알고리즘을 쓸 수 있음. 큐 사이 이동은 불가
MFQ (Multilevel Feedback Queue)MLQ에서 한 단계 발전 — 프로세스가 CPU를 많이 쓸수록 하위 큐로 이동시켜, 입출력 위주/CPU 위주 프로세스에 서로 다른 시간 할당량을 준다 (하위 큐일수록 할당시간을 크게)
MFQ의 아이디어: "CPU를 오래 쓰는 놈은 급한 일이 아니다"라고 판단해 아래 큐로 내려보낸다. 반대로 금방 입출력하러 나가는 프로세스(대화형 작업)는 위 큐에 남아 빠른 응답을 받는다. 사용자가 타이핑하는 동안 화면이 버벅이지 않는 이유가 이것이다.

📌시험 빈출 포인트

  • 비선점 = FCFS·SJF·HRN(HRRN), 선점 = RR·SRT·MLQ·MFQ — 분류 문제 매년 출제
  • 반환시간 = 완료 − 도착, 대기시간 = 반환 − 실행 — 도착시각 빼는 것을 절대 잊지 말 것
  • FCFS/SJF/SRT/RR/HRRN 각각의 평균 대기시간·반환시간 계산 문제 (간트차트 그리기가 핵심)
  • SRT = SJF의 선점 버전, 도착 시점마다 남은 시간 비교
  • 기아상태 발생 가능: SJF, SRT, 우선순위 / 기아상태 없음: FCFS, RR, HRRN
  • 기아상태 해결책 = Aging(노화) 또는 HRN 방식 적용
  • RR의 Time Slice가 너무 크면 FCFS와 동일, 너무 작으면 문맥교환 오버헤드 증가
  • 우선순위 스케줄링은 선점·비선점 둘 다 가능 ("항상 선점 방식"이라는 표현은 오답)
  • HRRN 공식: (대기시간+서비스시간) ÷ 서비스시간, 값이 클수록 우선
  • MLQ는 큐 이동 불가, MFQ는 큐 이동 가능

정답 ③ 5초

  1. FCFS이므로 도착 순서 그대로 P1 → P2 → P3 → P4

정답 ② 7초

SRT는 도착 시점마다 딱 한 번씩 비교하면 된다. 비교표를 만들어 따라가자.

  1. t=0 P1만 있음 → P1 실행
  2. t=2 P2 도착. P1 남음 6 vs P2 4 → P2 선점
  3. t=4 P3 도착. P2 남음 2 vs P3 1 → P3 선점
  4. t=5 P3 완료. P1(6) vs P2(2) → P2 재개
  5. t=6 P4 도착. P2 남음 1 vs P4 4 → P2가 짧으므로 그대로 진행, t=7 완료
  6. t=7 P1(6) vs P4(4) → P4 실행, t=11 완료
  7. t=11 마지막 P1이 6초 실행 → t=17 완료
  8. 반환시간 = 완료 − 도착 → P1 = 17, P2 = 5, P3 = 1, P4 = 5
  9. 평균 = (17 + 5 + 1 + 5) ÷ 4 = 28 ÷ 4 = 7초

함정 두 가지: ① t=6에서 "새 프로세스가 왔으니 바꿔야 하나?" 싶지만, 남은 시간이 더 짧으면 안 바꾼다(P2 1 < P4 4). ② 가장 먼저 도착한 P1이 가장 늦게 끝난다는 결과가 직관에 반해 보여도 정상이다 — SRT에서 긴 작업은 계속 밀린다.

정답 ① 5.7초

RR은 준비 큐의 순서를 매 순간 적어가는 것이 핵심이다.

  1. t=0~2 P1 실행 (잔여 1). 도중 t=1에 P2 도착 → 큐 [P2]
  2. t=2 P1 할당량 소진 → 큐 맨 뒤로. 큐 [P1(1)] → P2 실행(2~4)
  3. t=3 P3 도착 → 큐 [P1(1), P3]
  4. t=4 P2 할당량 소진(잔여 2) → 맨 뒤로. 큐 [P1(1), P3, P2(2)] → P1 실행(4~5) 후 완료

  6. t=7~9 P2 실행 → 완료(t=9)

함정: t=4에서 큐 맨 앞이 누구인지가 갈림길이다. P1이 t=2에 큐에 들어갔고 P3는 t=3에 들어갔으므로 P1이 앞이다. 순서를 뒤집으면 답이 6.0(②)이 되어 오답 선택지에 정확히 걸린다.

공식 (대기시간 + 서비스시간) ÷ 서비스시간에 그대로 대입한다.

문제 82021 국회직 · 기출문제집 p.203

선점형(Preemptive) 스케줄링에 해당하지 않는 것은?

  1. MFQ(Multilevel Feedback Queue) 스케줄링
  2. RR(Round Robin) 스케줄링
  3. MLQ(Multilevel Queue) 스케줄링
  4. SRT(Shortest Remaining Time) 스케줄링
  5. HRN(Highest Response ratio Next) 스케줄링
해설 보기

정답 ⑤ HRN

  1. HRN은 다음에 실행할 프로세스를 고를 때만 응답률 공식을 쓴다 — 일단 CPU를 잡으면 끝까지 실행
  2. 따라서 HRN은 비선점이며, 나머지 MFQ·RR·MLQ·SRT는 전부 선점형

헷갈리는 이유: HRN은 "대기시간에 따라 우선순위가 계속 바뀐다"는 설명 때문에 선점처럼 느껴진다. 하지만 우선순위가 바뀌는 것과 실행 중인 것을 뺏는 것은 별개다. HRN은 순위표만 갱신할 뿐, 이미 실행 중인 프로세스를 끌어내리지는 않는다.

문제 9개념 확인 · 응용

RR 스케줄링에서 시간 할당량(Time Quantum)을 무한히 크게 설정하면 어떤 알고리즘과 동일하게 동작하는가? 그리고 반대로 아주 작게 하면 어떤 문제가 생기는가?

해설 보기

정답: 할당량이 매우 크면 FCFS와 동일 / 매우 작으면 문맥교환 오버헤드 급증

  1. 할당량이 모든 프로세스의 실행시간보다 크면 아무도 중간에 잘리지 않는다 → 도착 순서대로 끝까지 실행 = FCFS
  2. 반대로 할당량이 아주 작으면 프로세스가 조금 실행되다 계속 교체된다 → 문맥교환 횟수 급증
  3. 문맥교환은 그 자체로는 아무 일도 하지 않는 순수 오버헤드이므로, 실제 작업 처리 시간 비중이 줄어 전체 성능이 떨어진다

결론: Time Quantum은 너무 커도(공평성 상실) 너무 작아도(오버헤드) 안 되는 트레이드오프 값이다. 이 구조를 묻는 서술형·객관식이 자주 나온다.
