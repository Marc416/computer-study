소프트웨어 생명주기 (SDLC)

개발 모델 · 비용 산정 · 일정 계획(CPM) · PART 06. 소프트웨어공학

핵심 요약

SDLC(Software Development Life Cycle) 표준 순서는 계획 → 분석 → 설계 → 구현 → 테스트 → 유지보수다.

각 개발 모델(폭포수·프로토타입·나선형·애자일)은 이 6단계를 "어떤 순서/반복 방식으로 밟느냐"가 다를 뿐이다.

계획 단계의 계산 문제 3종 — LOC 기반 기간 산정 · 기능점수(FP) · CPM 임계경로 — 는 거의 매년 나온다.

🎯이 단원을 왜 배우나

"그냥 만들면 되지 왜 모델이 필요한가"

혼자 만드는 200줄짜리 프로그램은 그냥 짜면 된다. 그런데 20명이 2년 동안 50만 줄을 만든다고 해보자. 누가 언제 무엇을 끝내야 다음 사람이 시작할 수 있는지, 고객이 "생각해보니 이게 아니었다"고 할 때 어디까지 되돌려야 하는지가 즉시 문제가 된다. 소프트웨어는 눈에 보이지 않아서 진척도를 눈으로 확인할 수 없다는 점이 건설·제조업과 결정적으로 다르다.

그래서 나온 것이 생명주기 모델이다. 핵심 질문은 딱 하나다 — "고객에게 결과물을 언제 보여줄 것인가?" 끝까지 다 만들고 보여주면 폭포수, 시제품을 먼저 보여주면 프로토타입, 위험한 것부터 조금씩 돌려가며 보여주면 나선형, 2주마다 계속 보여주면 애자일이다. 모델 이름을 외우기 전에 이 한 줄을 잡아두면 거의 모든 문제가 풀린다.

그리고 계획 단계에서는 "얼마나 걸리고 얼마나 드는가"를 숫자로 답해야 한다. 그 도구가 LOC·COCOMO·기능점수(규모 추정)와 CPM·간트차트(일정 추정)다. 시험은 이 부분을 계산 문제로 낸다.

💡주요 개념 — 개발 모델

SDLC 6단계 순서 📖 기출문제집 p.606~607

시험은 순서를 살짝 뒤섞어서 "옳은 것은?" 형태로 자주 낸다. 실제 기출 선택지 예시:

  1. ① 계획 — 분석 — 설계 — 구현 — 테스트 — 유지보수 ← 정답
  2. ② 분석 — 계획 — 설계 — 구현 — 테스트 — 유지보수 (계획·분석 순서가 바뀜 → 오답)
  3. ③ 분석 — 계획 — 설계 — 테스트 — 구현 — 유지보수 (테스트·구현 순서가 바뀜 → 오답)
  4. ④ 계획 — 설계 — 분석 — 구현 — 테스트 — 유지보수 (설계·분석 순서가 바뀜 → 오답)
암기 순서: "계획 없이 분석 못하고, 분석 없이 설계 못하고, 설계 없이 못 만들고(구현), 만든 건 테스트하고, 다 끝나도 고쳐야(유지보수) 한다" — 당연한 흐름이라 순서 자체는 상식적으로 유추 가능.
표기 차이 주의: 폭포수 모형을 세분화하면 계획 → 요구분석 → 설계 → 구현 → 시험 → 인수/설치 → 유지보수가 된다. 문제마다 "분석/요구분석", "테스트/시험"처럼 표기가 다르니 단어가 아니라 순서로 판단할 것.

4대 모델의 흐름 비교 (한눈에 보기)

모델별 상세 — 시험에 나오는 문장들

폭포수(Waterfall) 📖 p.608~609

  • 1950년대 항공 방위 소프트웨어 개발 경험에서 나온 가장 오래되고 널리 쓰인 모델
  • 각 단계가 순차적 — 병행 진행도, 거슬러 반복도 없다. 이전 단계가 끝나야 다음 단계 시작
  • 단계마다 나와야 할 중간 산출물(deliverable)이 명확히 정의되어 있다 → 문서화·관리가 쉽다
  • 단점: 고객 요구를 초기에 완벽히 기술하기 어렵고, 동작하는 시스템이 후반부에야 나오므로 중요한 문제가 늦게 발견된다
  • 적합: 요구사항이 잘 이해되고 개발 중 급격한 변경이 없는 경우

프로토타입(Prototype, 원형) 📖 p.609~610

  • 순서: 요구분석 → 시제품 설계 → 시제품 개발 → 고객 평가 → 시제품 정제 → 완제품 생산
  • 목적은 초기에 고객 요구를 제대로 뽑아내는 것 — 발주자가 목표 시스템을 미리 볼 수 있다
  • 프로토타입은 품질보다 속도가 중요하며, 만든 뒤 폐기될 수도 재사용될 수도 있다
  • 사용자 요구가 불투명할 때 폭포수를 대체할 수 있는 방법. 시스템 이해도가 낮은 관리자가 있을 때 유용

자주 나오는 함정 ①: "프로토타입 모형의 마지막 단계는 설계이다" → ✗ 마지막은 완제품 생산. 함정 ②: "가장 오래되고 널리 사용된 방법" → ✗ 그건 폭포수다.

나선형(Spiral) 📖 p.611~613

  • 보헴(Boehm)이 제안. 폭포수 + 프로토타입의 장점에 "위험 분석"을 추가한 모델
  • 한 바퀴(나선) = ① 계획 및 정의 → ② 위험 분석 → ③ 개발 및 검증 → ④ 고객 평가 의 4단계
  • 비선형적·반복적으로 진행되므로 소프트웨어 품질 중 강인성(robustness)을 높일 수 있다
  • 대규모 시스템에 가장 적합 (소규모에 적합하다는 선택지는 오답)
  • 단점: 초기 위험 분석을 잘못하면 많은 비용을 쓰고도 실패할 수 있고, 관리가 복잡하다

위험의 3분류: 프로젝트 위험(인력부족·관리변화·하드웨어 미비·규모 과소평가) / 프로덕트 위험(요구변경·명세서 지연) / 비즈니스 위험(기술변화·생산품 경쟁)

자주 나오는 함정: "3단계(계획·개발·평가)로 이루어진다" → ✗ 위험 분석을 포함한 4단계다. "소규모에 적합" → ✗ 대규모.

V 모델 📖 p.613~614

  • 폭포수의 변형 — 산출물보다 각 개발 단계의 "테스트와 검증"에 중점
  • 순서: 요구분석 → 시스템설계 → 상세설계 → 코딩 → 단위테스트 → 통합테스트 → 시스템테스트 → 인수/설치
  • 왼쪽(개발)과 오른쪽(테스트)이 짝을 이룬다 — 상세설계↔단위테스트, 시스템설계↔통합/시스템테스트
  • 높은 신뢰성이 요구되는 분야에 적합. V자 모양 그림은 테스트 문서 참고

애자일(Agile)과 XP 📖 p.617~619

애자일 4대 가치 — 시험에 거의 그대로 나온다:

  1. 프로세스와 도구 중심이 아닌 → 개인과 상호 소통
  2. 문서 중심이 아닌 → 실행 가능한(동작하는) 소프트웨어
  3. 계약·협상 중심이 아닌 → 고객과의 협력
  4. 계획 중심이 아닌 → 변화에 대한 민첩한 대응

짧은 릴리즈 주기(small release)로 점증적으로 개발하고, 각 반복 종료마다 완성된 시스템을 고객에게 인도해 피드백을 받는다. 개발 후반에 추가되는 요구사항도 기꺼이 받아들인다.

XP(익스트림 프로그래밍): 애자일의 한 종류. 켄트 벡이 고안. 가치는 의사소통·단순성·피드백·용기(+ 존중). 요구 변화가 잦은 소규모 팀 프로젝트에 효과적.

UP(Unified Process): 반복적·점진적, 유스케이스 기반, 아키텍처 중심, 위험 관리 중시. "모든 요구사항을 초기에 완전히 파악하도록 요구한다"는 서술은 오답(반복 모델이므로).

🧮주요 개념 — 계획 단계의 계산 (비용·일정)

규모·비용 추정 방법 📖 기출문제집 p.622~624

함정: 나씨-슈나이더만(NS) 도표는 계획 도구가 아니라 설계(알고리즘 표현) 도구다. "계획 단계의 도구를 모두 고르시오"에서 NS 도표가 섞여 나온다.

기능점수(Function Point)는 왜 만들어졌나

COCOMO·LOC 방식은 "코드 몇 줄인가"로 규모를 잰다. 그런데 같은 기능도 언어에 따라 줄 수가 3배씩 차이나고, 개발 전에는 줄 수를 알 수도 없다. 이 부정확함을 개선하려고 나온 것이 기능점수다.

기능점수는 라인 수 대신 입력·출력·조회·파일·인터페이스의 개수와 복잡도로 점수를 매긴다. 그래서 구현 방법·개발 언어와 무관하고, 계획 단계부터 분석·설계·구현 단계까지 전 단계에서 사용 가능하다.

측정 요소 5가지: 내부논리파일(ILF), 외부연계파일(EIF), 외부입력(EI), 외부출력(EO), 외부조회(EQ)

함정 ①: "트랜잭션 측정 기준은 내부입력·내부출력·내부조회" → ✗ 전부 외부(External)다. 함정 ②: "측정의 일관성을 위해 개발 기술·방법·품질 수준을 고려한다" → ✗ 고려하지 않는다. 함정 ③: 기능점수 산정 시 원시 코드 라인 수는 고려하지 않는다.

CPM 임계경로 — 계산하는 법

CPM은 "작업들의 선후 관계를 네트워크로 그렸을 때 전체 프로젝트가 최소 얼마나 걸리는가"를 구하는 방법이다. 답은 항상 시작에서 끝까지 가는 경로 중 가장 긴 것이다. 가장 긴 경로가 안 끝나면 프로젝트가 안 끝나기 때문이다.

CPM 3종 공식
• ES(가장 빠른 착수일) = 선행 작업들이 전부 끝나는 시점 = 선행 경로 중 가장 긴 것
• LS(가장 늦은 착수일) = 전체 기간 − (그 작업부터 끝까지 가는 경로 길이)
• 여유기간(slack) = LS − ES  →  임계경로 위에서는 0

📌시험 빈출 포인트

  • SDLC 표준 순서: 계획 → 분석 → 설계 → 구현 → 테스트 → 유지보수 (순서 뒤섞은 오답 선택지 주의)
  • 폭포수 모델은 되돌아가는 흐름이 없다 — 유일하게 "일직선"인 모델, 단계별 산출물 관리를 강조
  • 나선형 모델의 핵심 키워드는 위험 분석(Risk Analysis), 4단계, 보헴, 대규모 시스템
  • 프로토타입 모델은 "시제품 → 평가 → 재개발" 루프가 있고, 마지막 단계는 완제품 생산
  • V 모델 = 폭포수 + 테스트/검증 강조, 단계 순서(시스템설계→상세설계→코딩→단위→통합→시스템테스트)
  • 애자일은 문서보다 동작하는 소프트웨어, 점증적 개발, 후반 요구 변경도 수용
  • XP는 켄트 벡, 가치 = 의사소통·단순성·피드백·용기
  • LOC 기간 계산: 전체 LOC ÷ (인원수 × 1인당 월 생산성)
  • 기능점수는 라인 수와 무관, 외부입력/외부출력/외부조회 기준, 전 생명주기 단계에서 사용 가능
  • CPM 임계경로 = 가장 긴 경로, 임계경로 작업의 여유기간 = 0
  • 상위 CASE = 분석·설계 지원, 하위 CASE = 코딩·문서화 지원

문제 52016 국회 · 기출문제집 p.622

개발할 프로그램의 LOC(Line of Code)가 50,000이고 개발에 참여할 프로그래머가 5명, 각 프로그래머들의 평균 생산성이 1,000 LOC/MM(Man-Month)일 때 개발에 소요되는 기간은?

  1. 10개월
  2. 15개월
  3. 20개월
  4. 30개월
해설 보기

정답 ① 10개월

단위를 따라가면 자동으로 풀린다. MM(Man-Month) = 한 사람이 한 달 동안 하는 일의 양이다.

  1. 1인당 생산성 = 1,000 LOC / 월
  2. 5명이 함께 일하면 팀 전체 생산성 = 1,000 × 5 = 5,000 LOC / 월
  3. 필요 기간 = 전체 규모 ÷ 팀 생산성 = 50,000 ÷ 5,000 = 10개월

공식: 기간 = 전체 LOC ÷ (인원수 × 1인당 월 생산성)

함정: ⑤ 50개월류의 선택지는 인원수로 나누는 것을 빼먹은 경우(50,000÷1,000)다. "몇 명이 함께 하는가"를 반드시 곱할 것.

문제 62019 계리직 · 기출문제집 p.624

작업 분할을 통해 파악된 다음 소작업 목록을 AOE(Activity On Edge) 네트워크로 표현하였을 때, 이 프로젝트가 끝날 수 있는 가장 빠른 소요시간은?

소작업abcdefg
소요시간5582345
선행 소작업없음없음a, bcb, cde, f
  1. 13
  2. 21
  3. 24
  4. 32
해설 보기

정답 ③ 24

각 작업의 완료 시각을 앞에서부터 차례로 구하면 된다. 규칙은 하나 — "선행 작업이 여러 개면 그중 가장 늦게 끝나는 것을 기다린다(= max)".

  1. a: 선행 없음 → 0에 시작, 5에 끝남. b: 선행 없음 → 0에 시작, 5에 끝남
  2. c: 선행 a(5), b(5) → max(5,5)=5에 시작 + 8 = 13에 끝남
  3. d: 선행 c(13) → 13 + 2 = 15에 끝남
  4. e: 선행 b(5), c(13) → max(5,13)=13에 시작 + 3 = 16에 끝남
  5. f: 선행 d(15) → 15 + 4 = 19에 끝남
  6. g: 선행 e(16), f(19) → max(16,19)=19에 시작 + 5 = 24에 끝남 → 전체 기간 24

함정: ② 21은 g의 선행에서 max 대신 e(16)를 골라 16+5로 계산한 경우다. 선행 작업이 둘 이상이면 무조건 늦은 쪽을 기다려야 한다는 것이 이 유형의 전부다.

문제 72012 계리직 · 기출문제집 p.628

다음 CPM 소작업 리스트에서 작업 C의 가장 빠른 착수일(ES), 가장 늦은 착수일(LS), 여유 기간(slack)을 순서대로 나열한 것은?

소작업선행 작업소요 기간(일)
A없음15
B없음10
CA, B10
DB25
EC15
  1. 15일, 15일, 0일
  2. 10일, 15일, 5일
  3. 10일, 25일, 5일
  4. 15일, 25일, 0일
해설 보기

정답 ① 15일, 15일, 0일

  1. 전체 기간 먼저 구하기: 경로는 A→C→E = 15+10+15 = 40, B→C→E = 10+10+15 = 35, B→D = 10+25 = 35 → 전체 기간 = 가장 긴 40일
  2. ES(C): C는 A(15일)와 B(10일)가 둘 다 끝나야 시작 → max(15, 10) = 15일
  3. LS(C): 전체 40일에서 C 이후로 남은 작업량을 뺀다 → 40 − (C 10일 + E 15일) = 40 − 25 = 15일
  4. slack = LS − ES = 15 − 15 = 0일

의미: slack이 0이라는 것은 C가 임계경로 위에 있다는 뜻 — C가 하루라도 늦으면 프로젝트 전체가 하루 늦는다.

함정: ②·③처럼 ES를 10일로 잡는 것은 선행 작업 중 빨리 끝나는 B만 보고 계산한 실수다. 선행이 여럿이면 항상 가장 늦게 끝나는 것을 기다린다.

문제 82019 국가직 · 기출문제집 p.623

소프트웨어 규모를 예측하기 위한 기능점수(function point)를 산정할 때 고려하지 않는 것은?

  1. 내부논리파일(Internal Logical File)
  2. 외부입력(External Input)
  3. 외부조회(External inQuiry)
  4. 원시 코드 라인 수(Line Of Code)
해설 보기

정답 ④ 원시 코드 라인 수(LOC)

기능점수가 태어난 이유 자체가 이 문제의 답이다. COCOMO·LOC 방식이 쓰던 "코드 라인 수"가 부정확해서(언어마다 다르고 개발 전엔 알 수도 없음) 그걸 버리려고 만든 것이 기능점수다.

  1. 기능점수는 라인 수 대신 기능의 개수와 복잡도로 점수를 매긴다
  2. 측정 대상: 내부논리파일(ILF), 외부연계파일(EIF), 외부입력(EI), 외부출력(EO), 외부조회(EQ)
  3. 따라서 ①②③은 모두 측정 요소이고, ④ LOC만 기능점수와 무관

같이 외울 함정: 트랜잭션 측정 기준은 외부입력·외부출력·외부조회다. "내부입력·내부출력"으로 바꿔 쓴 선택지가 자주 나온다.

문제 9개념 확인 · 응용

어떤 프로젝트의 전체 규모가 120,000 LOC이고, 투입 가능한 프로그래머는 8명, 1인당 평균 생산성은 500 LOC/MM이다. 개발 기간은 몇 개월인가? 또, 기간을 절반으로 줄이려면 이론상 몇 명이 필요한가?

해설 보기

정답: 30개월, 기간을 절반(15개월)으로 줄이려면 이론상 16명

  1. 팀 전체 생산성 = 8명 × 500 = 4,000 LOC/월
  2. 기간 = 120,000 ÷ 4,000 = 30개월
  3. 15개월로 줄이려면 필요한 월 생산성 = 120,000 ÷ 15 = 8,000 LOC/월
  4. 필요 인원 = 8,000 ÷ 500 = 16명 (현재의 2배)

실제로는 이렇게 안 된다 (브룩스의 법칙): 사람을 2배 넣는다고 기간이 정확히 절반이 되지는 않는다. 인원이 늘면 의사소통 경로가 급증하고 신규 인력 교육 비용이 들어서, "지연된 프로젝트에 인력을 추가하면 더 늦어진다"는 말이 나온다. 시험 계산 문제에서는 이상적인 비례 관계로 풀되, 서술형 선택지에서 "인원을 늘리면 항상 기간이 비례해서 준다"는 문장이 나오면 오답으로 판단할 것.
