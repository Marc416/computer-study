# 빌드 과정 (전처리기 → 컴파일러 → 어셈블러 → 링커)

## 핵심 요약
> **전 → 컴 → 어 → 링** 순서로 소스코드가 실행파일이 된다.
> 3번째는 **어셈블러**, 최종 실행파일은 **링커**가 만든다.
> 암기법: **"전컴어링"**

## 주요 개념

### 1단계: 전처리기 (Preprocessor)
- `#include`, `#define` 등 **#으로 시작하는 지시문** 처리
- 헤더 파일 내용을 복사해서 붙여넣기
- 매크로를 실제 값으로 치환
- 결과물: **확장된 소스코드** (.i 파일)
- 비유: 레시피에서 "별첨 참고"를 실제 내용으로 교체하는 작업

#### 왜 전처리가 필요한가?
- C언어는 Java/Kotlin과 달리 `import`, `const val` 같은 편의 기능이 언어에 **내장되어 있지 않음**
- 그래서 **전처리기라는 별도 도우미**가 컴파일 전에 코드를 미리 정리해줌
- 전처리기는 **C/C++ 언어의 고유한 특징** (Java/Kotlin에는 없는 개념)

#### 전처리기가 하는 3가지
| 역할 | 예시 | 왜 필요? |
|------|------|----------|
| 코드 재사용 | `#include <stdio.h>` | 다른 파일의 코드를 가져다 쓰기 위해 (= Java의 import 역할) |
| 상수 관리 | `#define TAX_RATE 0.1` | 한 곳만 고치면 전체 반영 (= Kotlin의 const val 역할) |
| 조건부 컴파일 | `#ifdef WINDOWS` | 하나의 소스로 여러 환경(윈도우/맥/리눅스) 대응 |

#### 전처리 지시문(#) — Java/Kotlin 비교
| C 전처리기 | 역할 | Java/Kotlin 대응 |
|---|---|---|
| `#include <stdio.h>` | 파일 내용 통째로 복사 붙여넣기 | `import java.util.Scanner` (참조만 연결) |
| `#define MAX 100` | 텍스트 치환 (찾아바꾸기) | `const val MAX = 100` / `static final int MAX = 100` |
| `#ifdef DEBUG` | 조건부 컴파일 (코드 자체를 제거) | `if (BuildConfig.DEBUG)` (실행 시 분기, 코드는 남아있음) |

- **핵심 차이**: C의 `#`은 컴파일 전 **텍스트 수준 가공**(단순 찾아바꾸기), Java/Kotlin은 컴파일 중 타입 체크와 참조 연결
- **주의**: C의 `#`은 파이썬 주석(`#`)이나 마크다운 제목(`#`)과는 전혀 관계없음

### 2단계: 컴파일러 (Compiler)
- C 소스코드를 **어셈블리어**로 번역
- **문법 검사**(구문 분석), **최적화** 수행
- 결과물: **어셈블리 코드** (.s 파일)
- 비유: 한국어를 영어로 번역
- **주의**: 문법 검사와 최적화는 전처리기가 아니라 **컴파일러**의 역할!

### 3단계: 어셈블러 (Assembler)
- 어셈블리어를 **기계어(목적코드)**로 변환
- 결과물: **목적 파일(Object File)** (.obj / .o 파일)
- 비유: 영어를 로봇이 읽는 바코드로 변환

### 4단계: 링커 (Linker)
- 여러 목적 파일 + 라이브러리를 **하나로 결합**
- 외부 함수 참조를 실제 주소로 연결
- 결과물: **실행 파일** (.exe)
- 비유: 각각 만든 반찬을 한 상에 차리는 것

## 전체 흐름도

```
소스코드(.c)
    ↓ [전처리기] ← #include, #define 처리 (텍스트 가공)
확장된 소스(.i)
    ↓ [컴파일러] ← 문법 검사 + 최적화 + 번역
어셈블리 코드(.s)
    ↓ [어셈블러] ← 기계어로 변환
목적 코드(.obj)
    ↓ [링커] ← 라이브러리 연결, 파일 결합
실행 파일(.exe)
    ↓ [로더] ← 실행 시
메모리에 적재 → 실행
```

## 시험 빈출 포인트

- "3번째로 실행되는 것은?" → **어셈블러**
- 전처리기 결과물 → 확장된 소스코드
- 컴파일러 결과물 → **어셈블리어** (기계어 아님 주의!)
- 어셈블러 결과물 → **목적코드(Object Code)**
- 링커 결과물 → **실행 파일**
- 로더(Loader)는 빌드가 아니라 **실행 시** 메모리에 적재하는 역할
- 문법 검사, 최적화 → **컴파일러** (전처리기 아님!)
- 전처리기는 **C/C++의 특징** (Java/Kotlin에는 없음)
- "전처리기의 역할이 아닌 것은?" → 문법 검사, 최적화

## 헷갈리는 개념 비교

| 구분 | 전처리기 | 컴파일러 |
|------|----------|----------|
| 하는 일 | 텍스트 치환/복사/삭제 | 문법 검사 + 최적화 + 번역 |
| 수준 | 단순 텍스트 가공 | 언어 구조 분석 |
| 결과물 | 확장된 소스코드 (.i) | 어셈블리 코드 (.s) |

| 구분 | 컴파일러 | 어셈블러 |
|------|----------|----------|
| 입력 | 고급 언어(C 소스) | 어셈블리어 |
| 출력 | 어셈블리어 | 기계어(목적코드) |
| 변환 | 고급 → 저급 | 저급 → 기계어 |

| 구분 | 링커 | 로더 |
|------|------|------|
| 시점 | 빌드(컴파일) 시 | 실행 시 |
| 역할 | 목적파일 결합 → 실행파일 생성 | 실행파일을 메모리에 적재 |

| 기능 | C/C++ | Java/Kotlin |
|------|-------|-------------|
| 다른 파일 가져오기 | `#include` (전처리기) | `import` (언어 내장) |
| 상수 정의 | `#define` (전처리기) | `const val` (언어 내장) |
| 환경별 분기 | `#ifdef` (코드 자체 제거) | `if` (실행 시 분기) |
| 빌드 단계 | 4단계 (전처리→컴파일→어셈블→링크) | javac가 한 번에 바이트코드 생성 |
