# 프로젝트 계획 단계 도구

## 핵심 요약
> SDLC의 **"계획" 단계**에서 사용하는 도구들. 시험에서 "이건 계획 도구인가 설계 도구인가?"를 구분하는 문제가 나온다!

## 계획 단계 도구 분류

| 계획의 종류 | 도구 | 하는 일 |
|---|---|---|
| **노력 추정** (얼마나 힘든가?) | COCOMO | 코드 줄 수(LOC) 기반으로 비용 추정 |
| | **기능 점수(FP)** | 기능의 개수/복잡도로 규모 추정 |
| **일정 계획** (언제까지 하나?) | WBS | 업무를 작게 쪼개서 분류 |
| | **CPM** | 가장 오래 걸리는 경로(임계경로) 찾기 |
| | **간트 차트** | 일정을 막대 그래프로 표시 |
| **조직 계획** (누가 하나?) | 책임프로그래머 팀, 분산형 팀, 혼합형 팀 | 팀 구성 방식 결정 |

- 📌 출처: 2011 지방직 기출

## 🔍 각 도구 상세 설명

### 1️⃣ 노력 추정 — "이 프로젝트 얼마나 힘들어?"

#### COCOMO (COnstructive COst MOdel)

> 코드 줄 수(LOC)를 넣으면 → 필요한 인력/기간이 나오는 공식
> 비유: 이사할 때 **"짐이 몇 박스냐"**로 트럭 크기와 인부 수를 정하는 것

**📌 COCOMO 3단계 모델 (기출!)**

| 단계 | 영문 | 설명 | 비유 |
|------|------|------|------|
| 기본형 | Basic | LOC만으로 대략 계산 | 박스 수만 보고 견적 |
| 중간형 | Intermediate | LOC + 15개 비용 요인 반영 | 층수, 엘리베이터 유무 고려 |
| 발전형 | Detailed | 개발 단계별로 세분화 계산 | 방별 짐 종류까지 세밀하게 |

**📌 COCOMO 프로젝트 유형 3가지 (기출!)**

| 유형 | 영문 | 규모/특징 | 비유 |
|------|------|----------|------|
| 조직형 | Organic | 소규모, 경험 많은 팀 | 동네 이사 |
| 반분리형 | Semi-detached | 중간 규모, 혼합 경험 | 시내 이사 |
| 내장형 | Embedded | 대규모, HW 연동 | 해외 이사 |

💡 **암기**: **"조반내"** (조직형→반분리형→내장형) = 작은 것 → 큰 것

- 단점: 같은 기능이라도 프로그래머마다 코드 길이가 다름 → 부정확

---

#### 기능 점수 (Function Point)

> COCOMO(LOC)의 단점을 보완! **코드 줄 수에 의존하지 않음**
> **기능의 개수와 복잡도**로 규모를 측정
> 비유: 책 크기를 페이지 수(LOC)가 아니라 **챕터 수(기능)**로 재는 것

**📌 기능 점수의 5가지 요소 (기출!)**

| 요소 | 영문 | 쉬운 비유 |
|------|------|-----------|
| 내부논리파일 | ILF (Internal Logical File) | 우리 가게 장부 |
| 외부인터페이스파일 | EIF (External Interface File) | 다른 가게 장부 열람 |
| 외부입력 | EI (External Input) | 주문 접수 |
| 외부출력 | EO (External Output) | 영수증 발행 |
| 외부조회 | EQ (External inQuery) | 재고 확인 |

- ⚠️ **원시 코드 라인 수(LOC)는 기능 점수에 포함되지 않음!** (COCOMO에서 사용)
- 💡 암기: 기능 점수 = LOC 보완 → 당연히 LOC 안 씀
- 📌 출처: 2019 국가직 기출

### 2️⃣ 일정 계획 — "언제까지 끝내?"

#### WBS (Work Breakdown Structure) — "업무 쪼개기 트리"

> 큰 프로젝트를 작은 작업 단위로 **나무 구조**로 분해하는 기법
> 비유: 통닭을 한입에 못 먹으니 **부위별로 뜯는 것**

```
               [쇼핑몰 구축]
              /      |       \
         [프론트]  [백엔드]  [DB설계]
         /    \      |        |
     [메인]  [장바구니] [API개발] [테이블설계]
      페이지   페이지
```

💡 **핵심**: WBS 자체는 "일을 쪼개는 것"이고, 쪼갠 뒤 일정을 배치하는 건 간트 차트/CPM

### 3️⃣ 조직 계획 — "누가 하나?"

| 팀 구조 | 특징 | 비유 |
|---------|------|------|
| **책임프로그래머 팀** (Chief) | 한 명이 핵심 결정, 나머지 보조 | 수술실: 주치의 1명 + 간호사 |
| **분산형 팀** (Democratic) | 모두 동등, 민주적 결정 | 동아리 회의: 다 같이 토론 |
| **혼합형 팀** | 위 두 가지를 섞은 형태 | 팀장은 있지만 의견도 듣는 회사 |

💡 **시험 포인트**: "의사결정 빠른 팀?" → 책임프로그래머 / "만족도 높은 팀?" → 분산형

## 📊 도구별 시각적 예시 (이렇게 생겼다!)

### 간트 차트 (Gantt Chart) — "달력에 색칠한 막대"

가로축 = 시간, 세로축 = 작업. **막대 길이 = 작업 기간**. 학교 시간표나 노션 타임라인과 같은 모양!

```
작업        | 1주 | 2주 | 3주 | 4주 | 5주 |
------------|-----|-----|-----|-----|-----|
요구분석     |████ |████ |     |     |     |
설계        |     |████ |████ |     |     |
구현        |     |     |████ |████ |     |
테스트      |     |     |     |████ |████ |
```

💡 **한 줄 요약**: 일정을 막대 그래프로 보여주는 도구 → **"누가 언제까지 뭘 하나"**

---

### CPM (Critical Path Method) — "가장 느린 놈이 전체 속도 결정"

동그라미(작업) + 화살표(순서)로 네트워크 그래프를 그린 뒤, **가장 오래 걸리는 경로**를 찾음

```
        (설계:3일)       (테스트:2일)
  [시작] ──────→ [B] ──────────→ [끝]
    │                              ↑
    │  (DB구축:5일)   (연동:1일)   │
    └──────→ [C] ──────→ [D] ─────┘
```

- 경로1: 3+2 = **5일**
- 경로2: 5+1 = **6일** ← 🔴 **임계경로(Critical Path)!**
- 전체 최소 기간 = **6일** (가장 긴 경로)

💡 **비유**: 배달 3개 시키면 제일 늦은 배달이 와야 식사 시작 = 임계경로

---

### 나씨-슈나이더만 (Nassi-Shneiderman) — "상자 안에 로직 채우기" ⚠️설계 도구!

화살표 없이 **네모 상자만으로** 순차/선택/반복을 표현. 순서도의 변형.

```
┌─────────────────────────┐
│    점수를 입력받는다       │  ← 순차
├────────────┬────────────┤
│  점수≥60   │   점수<60   │  ← 선택(if/else)
├────────────┤────────────┤
│  "합격"출력 │ "불합격"출력 │
├────────────┴────────────┤
│    결과를 저장한다        │  ← 순차
└─────────────────────────┘
```

🚨 **시험 함정**: 나씨-슈나이더만은 **설계 도구**이지 계획 도구가 아님!

---

### 기능 점수 (Function Point) — "기능 개수로 크기 측정"

코드 줄 수(LOC)가 아니라 기능의 수와 복잡도로 소프트웨어 규모를 산정

```
기능 점수 산정 예시 (쇼핑몰)
──────────────────────────────────
내부논리파일(ILF): 회원DB, 상품DB     → 2개
외부인터페이스(EIF): 결제사 연동       → 1개
외부입력(EI): 회원가입, 상품등록       → 2개
외부출력(EO): 주문내역서, 매출보고서    → 2개
외부조회(EQ): 재고조회, 배송추적       → 2개
──────────────────────────────────
→ 복잡도별 가중치 × 개수 = 기능 점수!
```

💡 **LOC vs FP**: LOC는 프로그래머마다 코드 길이가 달라서 불공평 → FP는 기능 기준이라 객관적
